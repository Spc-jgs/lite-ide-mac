# 取代 IDEA：完整方案（设计稿，2026-10-22）

> 状态：**已拍板（2026-10-22）**：D6 同意、D7 数据库要做（放 MVP-7 之后、先写设计稿）、D8 自动更新器要做 + 插件只做声明式集成包（第 9 节）、D9 顺序改成 0 → 2 → 1。起因：用户 2026-10-22：「更多的是做取代 IDEA 的功能，让这个 IDE 更好用，该有的设置、界面、配置都要有，让它可以代替 IDEA；
> 先调研我给你的开源项目和 IDEA、VS Code、Sublime，出一个完整的方案 —— 缺什么、哪里欠缺、还需要什么功能、哪里不足、哪里补强、交互上哪里能做得更好；
> 要完整的设计，然后分 MVP 执行，允许重构，允许大修大动。」
>
> 和已有文档的关系：[DIRECTION.md](DIRECTION.md) 是定位和优先级、[IDEA.md](IDEA.md) 是「接住 IDEA 的 Java 后端日常」那一轮的设计和全过程（27 节）。
> 这份是**下一阶段的总图**：从「接住日常」走到「能代替」。IDEA.md 第 3 节的硬约束（秒开不等、独立进程可关、不打断、每步量数字）照旧是每一步的审。

## 0. 结论

1. **离「能代替 IDEA」差的不是大件，是一长串中小件。** 大件（Maven、Spring Boot 启动、jdtls 的补全 / 改名 / 修复 / 格式化、单测、调试、热替换、HTTP、本地历史、Git 全家桶）都有了，
   而且有几处比 IDEA 好（秒开、日志、跨文件替换可撤销、从不让人等）。差的是**每天碰十几次的那些小动作**：跳到实现、类型层级、看文档、⇧⇧ 搜类、问题列表、
   生成 getter、重新打开刚关的标签、工具窗的编号键 —— 少一个，人就想回 IDEA。
2. **最便宜的一批是「jdtls 早就会、我们没接」**：现在只接了 jdtls 的 8 种请求（定义、用法、补全、修复、格式化、改名、参数提示、诊断），
   实现、类型 / 调用层级、全项目符号、悬停文档、语义着色、内嵌提示、同名高亮、代码生成都现成，只差接线和界面 —— 第一期就做这批。
3. **设置是第二大缺口**：现在 14 个设置项，IDEA 几百个。不追数量，按「换过来的人第一周会去找的」补齐一棵完整的树（第 6 节），加上**键位可改**和**浅色主题**。
4. **要大修的有四处**（第 7 节）：运行配置统一成一个模型（现在 tasks.json、Spring 自动识别、运行配置对话框三套并存）、工具窗系统（现在左边导轨是写死的）、
   键位从「写死的表」变成「默认 + 你的覆盖」、语言服务从「Java 专用」泛化成「按语言接」。
5. **分 9 期（MVP-0 到 MVP-8）**，每期都能单独用上、单独验收（第 8 节）。先清 bug，再接 jdtls 的便宜货，再做运行配置和工具窗的大修 —— 后面几期都踩在它们上面。

## 7. 要大修的四处（允许重构）

### R1 运行配置统一成一个模型

**现在**三套并存：`tasks.json`（任务运行，#48）、Spring 自动识别 + `projectcfg` 的运行配置（10-22）、Maven 工具窗的勾选（`maven-prefs.json`）。
人要问「VM 参数在哪改」，代码里「起一个东西」有三条路。

**改成**：一个 `RunConfig { name, kind, 公共项（环境变量、工作目录、起之前做什么）, 按类型的项 }`，类型是 Spring Boot / Application / JUnit / Maven / npm / Python / Shell / HTTP / 组合。
- 来源有三种、合成一张表：**认出来的**（Spring、package.json scripts、pom 里的入口 —— 不存，每次现认）、**你建的**（存应用目录）、**项目里的**（`tasks.json` 照旧认、以后 `.run/`）。
  认出来的你一改就变成「你建的」（IDEA 的 temporary → permanent 同一个意思）。
- 命令都从一个地方拼（现在 Spring 在 `maven::run_command`、任务在 `taskdefs`）；调试、热替换插 agent 的那个「`exec java `」形状保住。
- 界面：顶栏一个下拉（当前配置）+ ▶ 🐞 ■；「运行 / 调试配置」对话框左边按类型分组、`+` 新建。
- 迁移：`projectcfg` 的运行配置原样搬进新表；`tasks.json` 不动（它是项目文件）。

### R2 工具窗系统

**现在**：左边导轨的按钮写死在 `Rail.svelte`，底部面板、Services、调试、Maven 各有各的开法。

**改成**：一张工具窗登记表 `{ id, 名字, 图标, 默认在哪条边, 编号键, 懒加载的组件 }`，左 / 右 / 下三条边，拖动换边，布局存 `ui-state.json`（按窗口）。
编号键照 IDEA（G7）。现有的每个面板挪进来一个一个挪，每挪一个跑一遍 smoke。**入口包要守住**：登记表在入口，组件全是懒的。

### R3 键位：默认 + 你的覆盖

**现在**：`keymap.ts` 是唯一出处，菜单（Rust 的 `menu.rs`）照它建，测试卡着两边同步。好处是不会漂；坏处是改不了。

**改成**：`keymap.ts` 仍是**默认**；你的改动存 `keymap.json`（只存改过的）；生效表 = 默认 ⊕ 覆盖。Rust 建菜单时读生效表（菜单要能重建：改了键位不重启）。
`owner` 那一列的规矩照旧（菜单的键 webview 收不到，ui.md / keymap.ts 头上写着）—— 覆盖只能在同一个 owner 里改键，不能把一个 `cm6` 的动作改成菜单的。
`menu_sync.rs` 改成比「默认表」；另加一条测试：覆盖之后同一个键不许挂两个动作。

### R4 语言服务从「Java 专用」泛化

**现在**：`lspsvc` 本身是通用的（JSON-RPC、分帧、进程组、空闲收掉），但前端 `editor/java-lsp.ts`、Rust 的 `java.rs` 是写死给 jdtls 的。

**改成**：按语言一份配置 `{ 语言, 认哪些文件, 怎么起, 初始化参数, 支持哪些能力 }`；前端的补全 / 诊断 / 跳转 / 悬停 / 改名接通用的客户端，按能力开关。
Java 照旧内置；Python（basedpyright）、TS（typescript-language-server）按项目第一次用时问要不要下载（要 Node）。**这一步放在 MVP-1 之后**：
先在 Java 上把 MVP-1 那七八种请求接齐，再抽 —— 抽的时候知道「通用」到底要哪些口子，不是凭想象抽。

**D8 插件为什么是声明式集成包**（用户让我判断「真要代替 IDEA 和 VS Code，哪种最优、对以后的功能和开发和使用有帮助」）：

- VS Code、IDEA 的插件系统值钱的是**已经有的那几万个插件**。我们跑不了它们（VS Code 的扩展要它的 Node 扩展宿主和 API，IDEA 的要它的 JVM 平台），
  自己开一套完整的插件系统是从零生态开始 —— 代价全付、好处几乎拿不到。
- 「在应用里跑别人的代码」正是 `no-html-sinks` 那条规矩防的东西（一旦能跑别人的脚本就等于拿到这台机器）；公开的代码 API 要永远兼容，一个人加 AI 维护背不动；
  插件的运行时也会冲入口包的 160 KB 红线。
- 真正花力气的是「再接一门语言 / 一个构建工具」，而那件事的本质是数据：语言服务器怎么起、构建工具怎么调、认哪些文件、有哪些运行配置类型。
  做成 JSON 声明之后：R4 的泛化直接由它驱动；我们自己的 Java 支持就是第一个内置包；Python / TS / Go / Gradle 各是一个包；别人能自己加语言、不用改我们的代码。
  真跑代码的仍然是独立进程（语言服务器、构建工具），和跑任务同一个信任模型；要兼容的只是一份带版本号的 schema。
- Lithe 走的也是这条（它的插件契约写着「插件不在宿主进程内运行代码」）。

不做的：插件市场（装包是「从文件夹 / 地址装」，先问）、插件带的网页界面（Lithe 有，安全边界要单独设计，等真有人要）。
| D10 | 下载：JaCoCo agent（约 300KB，覆盖率）、Gradle（有 gradlew 不用）、Node + 两个语言服务器（MVP-7） | 到那一期再逐个问，说清是什么、从哪来、多大 |

## 10. 风险

- **大修期间行为倒退**：MVP-2 动的是外壳和运行，每天都在用。对策：每挪一块跑 smoke + spring.sh + tasks.sh；入口包每次量；不一次换完，一个工具窗一个工具窗地挪。
- **jdtls 的能力有上限**：IDEA 的几百种 intention、结构化搜索、深的 Spring 智能，jdtls 没有。第 5 节（IDEA.md）说过，这里不重复承诺。
- **内存**：每加一个语言服务器就是一个进程。守住「按项目、按需、空闲收掉、设置里能关」，每期量一次常驻。
- **一个人 + AI 的维护量**：设置项从 14 到七八十，每一项都是一条要验的路径。对策：设置项全从 DEFS 生成（不手写界面），验收按分类抽查。
