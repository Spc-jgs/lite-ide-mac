## 主题 1：子进程（2026-10-12）

读了：`process-hardening`（193 行，全读）、`utils/pty/src/{process_group,child_reaper,spawn_helper}.rs`、`core/src/exec.rs` 的常量和注释、
`core/src/shell_snapshot.rs` 的 `run_script_with_timeout`、`shell-command/src/shell_snapshot*.rs` 的结构、`sandboxing/src/seatbelt*.{rs,sbpl}` 的头部。

### 先说结论：我们的纪律和它的重合，这本身是证据

两个项目各自踩坑长出来的规矩，几乎一条条对得上：

| 规矩 | Codex | lite-ide |
|---|---|---|
| stdin 接空，绝不让子进程等输入 | 快照脚本 `stdin(/dev/null)` | `procutil::spawn` |
| 自己的进程组，停的时候整组 | `set_process_group` / `kill_process_group` | `tasksvc`、git fetch |
| 有时限，到点就杀 | 命令默认 10 秒、快照 10 秒 | 任务软停 5 秒宽限期；git 不设超时、靠取消（rust.md 有理由） |
| 丢掉就收尸 | `child_reaper` | `procutil::Running` 的 Drop、`Task` 的 Drop |
| 输出有上限 | `EXEC_OUTPUT_MAX_BYTES` | `run_capped` |

**不一样的地方才是要学的**，下面四条按对我们的价值排。

### 1. 后台孙进程攥着管道，我们会一直等下去（实测坐实，要修）

`core/src/exec.rs` 的 `IO_DRAIN_TIMEOUT_MS` 上面那段注释说的是：子进程派生的孙进程继承了 stdout / stderr，杀掉（或等到）子进程之后
管道还开着，读的那一方等不到 EOF，**整个 agent 卡死**。它的对策：子进程退出后，读管道最多再等 2 秒，到点放弃（不杀那个孙进程）。

我们的 `procutil::run_capped` 是「stdout 读到 EOF → wait → join stderr 线程」，三步都会等孙进程。临时加了一条测试实测（跑完删了）：

| 命令 | 多久回来 |
|---|---|
| `sleep 4 & echo hi`（后台的攥着 stdout、stderr） | **4.02 秒** |
| `sleep 4 >/dev/null & echo hi`（只攥着 stderr） | **4.02 秒** |
| `sleep 4 >/dev/null 2>&1 & echo hi`（都不攥） | 11 毫秒 |

后台那个不退，我们就永远不回来。**真实的入口是 `git commit` 的钩子**：钩子是仓库带来的（不是用户写的），一个
`post-commit` 里 `(做点什么) &` 没重定向输出，界面上的「提交」就一直转；git 写操作同一时间只许一个，之后所有 git 写操作都堵住，直到重启。
（git 自己的 `gc --auto` 后台化时会关掉 stdio，碰不上；碰得上的是写得随手的钩子。）

修法有两条，都记下来，还没定：
- **照 Codex：子进程退出后限时等管道**。`stdout` 也挪进 `drain` 线程，主线程 `wait()` 之后对两个线程各等一个上限，超了就拿已经读到的、
  把线程撒手（孙进程退了它自己会结束）。不杀孙进程 —— 钩子的后台活可能是用户想要的。
- 放进自己的进程组，子进程退出后 `killpg` 掉剩下的。更干净，但会杀掉钩子有意留下的后台活，**改变了用户的钩子的行为**，不选。

### 2. EPERM 不一定是「组里只剩僵尸」（实测，缺口真实但概率低）

`utils/pty/src/process_group.rs`：macOS 上 `killpg` 被拒（EPERM）时，用 `proc_listpgrppids` 列出组员、逐个发。
我们的 `tasksvc::group_alive` 把 EPERM 当「没有活的」，依据是第 0 步实测的「组里只剩没被回收的僵尸时 macOS 回 EPERM」。

实测（Python + ctypes，scratchpad 里）把几种组合摆出来：

| 组里有什么 | `killpg(组, 0)` | 信号送到了吗 |
|---|---|---|
| 活的组长 + 一个僵尸 | ok | 送到了，组长死了 |
| 活的 sh + `top`（setuid root，但**真实 uid 是我**）+ sleep | ok | 都死了 |
| 只剩一个僵尸 | **EPERM** | —— |

所以 EPERM 的来源是「组里有一个**真实 uid 不是我们**的进程」（典型是 `sudo` 正在以 root 跑命令），或者只剩僵尸。前一种情况下我们会误判成
「停干净了」、不再强杀。任务的 stdin 是空的，`sudo` 要密码会直接失败，所以**对我们是低概率**；Codex 的 agent 自己会跑 `sudo`，所以它必须处理。
要补的话照它：EPERM 时列组员，有不是僵尸的就算还活着。先记着，不排进优先级。

**测试手法值得学**：它把「发给组」「发给单个进程」做成参数（闭包）传进去，测试里直接注入一个 EPERM —— 不用真的造出一个 root 进程。
和我们把输出上限做成可注入（`run_raw_capped`）是同一个手法：**罕见的系统状态，注入，别去造**。

### 3. shell 快照：同一个问题，解法的规模跟调用频率走（对 #57 的判断）

Codex 每个会话跑一次用户的交互式 shell，把函数、`setopt`、别名、导出变量存成快照文件，之后每条命令加载快照、不再跑 rc。
`shell-command` 里这一块连测试 5,400 行，光是字面量转义 715 行，还有一份专门剔除凭据的。

我们每次起任务都 `$SHELL -ilc`（TASKS.md 第 10 节实测 0.33 秒）。#57 问的是要不要缓存。判断：

- Codex 一个会话跑几百条命令，每条省 0.3 秒值得 5,400 行；我们一天起几次任务，**0.33 秒不值得这么一套**。
- 真要做，做 VS Code 那种只缓存环境变量的：启动后跑一次 `$SHELL -ilc env`、带超时，缓存 PATH 那几样。函数、别名不管 ——
  任务命令要用 alias 的，本来就该写进脚本。
- #57 原来写的就是「先量再说」，这条读完更确定了：**量到 0.33 秒真成了问题再做**。

**通用经验**：看别人的方案先看它的调用频率和代价，再决定抄多少。直接抄一个为高频场景设计的东西，得到的是它的全部复杂度和一小部分收益。

### 4. 进程加固和沙箱：它防的人和我们不一样

`process-hardening` 在 `main` 之前做三件事：`ptrace(PT_DENY_ATTACH)` 不让调试器附加、`RLIMIT_CORE = 0` 不留 core 文件、删掉 `DYLD_*` 环境变量。
`sandboxing` 用 `/usr/bin/sandbox-exec` + 一份**默认全拒**的策略（照 Chrome 的写法）跑模型发起的命令，子进程继承同一个沙箱。

它防的是**同一个用户下、由模型发起的命令**：那些命令和 agent 同一个 uid，可以附加调试器读 agent 内存里的 API token、可以读 core 文件。
我们现在没有这种「替别人跑命令」的角色 —— 任务和终端都是用户自己写的命令，进程里也没有 token。**现在不学**；做 #46 时 agent 跑的命令在 agent 自己的沙箱里，
不在我们这边。

两个小细节是通用的：
- **调安全相关的程序写绝对路径**：它只认 `/usr/bin/sandbox-exec`，注释里说的理由是防有人在 PATH 前面放一个同名的。
- **默认全拒、逐条放行**，和我们 `gitsvc::trust` 的 config 白名单是同一个判据：黑名单永远在追下一个没想到的。

### 5. 还有两条，小，记着

- **procutil 的 Drop 是「kill 之后阻塞 wait」**。进程卡在不可中断的系统调用里（读一个断了线的网络卷）时，SIGKILL 要等那个调用返回才生效，
  `wait()` 跟着一直等。Codex 的 `child_reaper` 是一条全局线程轮询收尸，丢掉的那一下从不等。我们的调用点都在阻塞池里，影响是吃掉一条池线程；
  低概率，记着。
- **多线程进程里 fork 之后、exec 之前只能调「异步信号安全」的函数**（别的线程可能正攥着 malloc 的锁，子进程里只复制了当前线程，锁永远没人放）。
  Codex 在 Linux 上为此专门先起一个干净的小程序再 exec（`spawn_helper.rs`）。我们用 std 的 `process_group(0)`（走 `posix_spawn` 的属性，不在中间跑我们的代码），
  **别为了加功能写 `pre_exec`** —— 写了就得守这条。

## 主题 2：编辑器和 agent 怎么通信（2026-10-12）

读了：`app-server-protocol/src/rpc.rs`（全读）、`protocol/common.rs` 的 `server_request_definitions!` 那张表、`protocol/v1.rs` 的握手、
`app-server/src/outgoing_message.rs` 的发请求 / 取消 / 重放、`app-server-transport/src/transport/{stdio,mod}.rs`、`docs/protocol_v1.md` 的术语。

**先摆一个事实：Codex 不说 ACP。** 仓库里一处都没提。它和编辑器之间是自己的 app-server 协议（VS Code 插件走它）；ACP 是 Zed 牵头的跨 agent 标准，
Codex 要靠别人写的适配器才接得上。所以这一节学的是**做协议的手法**，不是我们要实现的那份协议。下面讲 ACP 的地方是我的了解，#46 第 0 步以它的官方 schema 核实。

### 1. 等人回话的请求不设超时，挂在「主人」身上（改我们的设计）

agent 反过来问编辑器的请求有 9 种（`server_request_definitions!`）：命令能不能跑、文件改动批不批、要用户补一句、要更多权限……几乎全是**问人**。
它们**一个超时都没有**。`outgoing_message.rs` 里的做法：

- 每个发出去的请求登记一条「id → 等结果的 oneshot」；发送失败当场摘掉，不留没人答的回调。
- 请求记着它属于哪个对话（thread）。对话被打断 → `cancel_requests_for_thread` 把属于它的全取消；连接断了 → 全取消。
- **客户端重新连上（界面重载）→ `replay_requests_to_connection_for_thread` 把还没答的再发一遍**，弹框不会凭空丢。
- 「登记之后再查一次」：断开的清理可能抢在登记之前跑完，登记完再看一眼连接还在不在，不在就自己摘掉 —— 和我们 `begin_run` 认领那种竞态是一个形状。

**这改了我们 DIRECTION 第 6 节的一句**：原来写「前端不回话的超时（ptysvc 背压那条同样适用）」。对**问人**的请求这是错的 —— 人可能只是走开了一会儿，
超时等于替他拒绝。要分两种：

| 请求 | 例子 | 怎么收尾 |
|---|---|---|
| 问人 | 权限卡片（ACP 的 `session/request_permission`） | 不超时。挂在会话和窗口上：会话取消 / 结束就取消它；窗口关了就取消（正好是 `Owned` + `release_window` 那套）；webview 重载就重放 |
| 问机器 | 要编辑器里的文件内容（ACP 的 `fs/read_text_file`） | 要超时，前端不答就报错给 agent（ptysvc 那条照旧适用） |

顺带一个可能更省事的方向（第 0 步评估）：「问机器」那种也许**根本不用反方向的往返**。没开着、或者开着但没改过的文件，Rust 直接读盘就对；只有「开着且有未保存改动」的
才要前端的内容 —— 前端可以在改动时把这些标签的内容推给 Rust（会话草稿本来就在定时落盘），Rust 自己答。代价是「推」有延迟，要量。

### 2. 编辑器没了，agent 靠 stdin 的 EOF 知道（回答「不留孤儿」）

`stdio.rs`：一行一条 JSON（ACP 也是），stdin 读到 EOF 就当客户端走了，开一个**只开一次**的看门线程：45 秒后无条件 `process::exit`。
**父进程不管怎么死的 —— 崩溃、被 kill -9 —— 内核都会关掉它那头的管道**，子进程读到 EOF。所以这条在我们 `panic = abort`、`Drop` 一个都不跑的时候也成立，
比我们任务那套「live.json 记账、下次启动收尸」更早、更直接。注释里一句很讲究：「这里别写日志，stderr 可能也堵着」—— 保证能退出的那段代码，自己不能有可能卡住的动作。

**但这是 agent 那头的规矩，我们管不了别人写的 agent。** #46 第 0 步要实测我们要接的那个 ACP agent：关掉它的 stdin，它退不退、多久退。
不退的话我们这边照任务那套：自己的进程组、关会话时整组先软后硬、账本兜崩溃。

### 3. 有界队列，满了就明说，不停下来不读

收件队列 128 条；满了对**请求**当场回一个「过载，稍后重试」的错误，对通知才等。停下来不读的话对方卡在写上 —— 正是 procutil 防的那个死锁换了个地方。
stdin、stdout 各占一条专门的阻塞线程（tokio 的 stdin 取消不了）。**我们接 agent 时同理**：agent 的 stdout 就是协议流，必须一直读；stderr 照 procutil 设闸排空。

### 4. 类型从一处生成，版本靠「默认关、客户端选开」

- 每个协议类型同时派生 `TS`（ts-rs，生成 TypeScript）和 `JsonSchema`；方法名、参数、返回类型写在一张宏表里，枚举、序列化、TS 都从它来。
  我们是两边手写、`dto_sync.rs` 卡漂移；它是生成，从根上不漂。**对 #46**：ACP 有官方 schema 和 Rust 实现（加依赖要先问），类型从那里来，别手抄一份。
- 新能力一律客户端在 `initialize` 里**选开**（`experimental_api`、`extensions`），新字段都 `#[serde(default)]`，旧接口标废弃但不删（v1 / v2 并存）。
  客户端还能声明「这几种通知我不要」。**通用经验**：协议的兼容性靠「新东西默认不出现」，而不是靠两边同时升级。
- 请求 id 各方向各自发号（服务端一个自增计数器）。和 rust.md「操作 id 由谁发」那条一致：谁发出请求谁定 id，而且**在发出之前**就定。

## 主题 3：给模型看的输出怎么截断（2026-10-12）

读了：`utils/output-truncation/src/lib.rs`（全读）、`utils/string/src/truncate.rs`、`core/src/tools/context.rs` 里命令结果交给模型的那段、
`core/src/unified_exec/{mod,head_tail_buffer}.rs`。

### 1. 两层，各管各的

| 层 | 上限 | 防什么 | 我们对应的 |
|---|---|---|---|
| 收输出 | 1MB（`DEFAULT_OUTPUT_BYTES_CAP`） | 一条跑飞的命令把进程内存撑爆 | procutil 的 `cap`、`MAX_DIFF_BYTES` |
| 交给模型 | 默认 1 万 token / 次，模型可以要得更少（取小的） | 一次工具结果吃光上下文 | 我们还没有 —— #46 之后才会有「我们拼东西给模型」 |

我们现在所有的上限都是第一层的用途（内存、渲染）。第二层的判据完全不同：**模型的上下文是按 token 计价、按 token 封顶的稀缺资源**，
省的不是内存，是「模型还能看多少别的东西」。

### 2. 截中间，不截尾巴；截了要说，而且给数字

- `truncate_middle_*`：预算两头对半分，留开头和结尾，中间换成 `…1234 tokens truncated…`。命令输出的开头是「跑了什么」，结尾是报错或结果，中间最不值钱。
- 截过的前面加一行 `Warning: truncated output (original token count: N)` 和总行数；第一层丢过字节的另有一个标记。
  **消费方是模型也一样：看着完整、其实少了一截的输出，比一句「放不下」危险** —— 和 rust.md「`truncated` 必须一路传到界面」是同一条规矩换了个消费方。
- 结果前面有一段**固定的头**：耗时、退出码、还在跑的话给会话 id、原始 token 数，然后才是 `Output:`。先给头留预算，截的只是正文 —— 元数据永远在。
  还预留了序列化的余量（`* 1.2`），免得后面存历史时按总预算把已经截过的再截一遍。
- 序列化成 JSON 时转义会让字符串变长，所以截 MCP 结果是**循环**的：截完量一次，超了按比例缩预算再截，直到放得下。

**截哪一头要看信息在哪**，我们现有的选择对照一下都站得住：差异留开头（人从上往下看）、搜索留前 N 条、`git status` 留前 N 条（砍到完整记录）、
端口报错**读结尾** 64KB（`port::from_log`，报错在最后）。**日志视图的 64KB 长行**（DIRECTION 第 7 节 P1）是唯一一处截了不说的 ——
修的时候照这里：行尾标「…还有 N KB 没显示…」，数字要真。

### 3. token 不数，按 4 字节估 —— 中文会估少

`approx_token_count` 就是 `字节数 / 4`（向上取整），不跑分词器：便宜、够用于「大概多少」。但中文在 UTF-8 里一个字 3 字节，按 4 字节一个 token 算，
**中文为主的文本会被估少**（具体差多少取决于分词器，我没有量过，方向上是少的）。我们的日志常常是中文：以后要按 token 给模型拼日志，别照搬这个估法，
至少按字符数估，或者干脆用模型给的计数接口。切的位置都对齐字符边界（`floor_char_boundary` / `ceil_char_boundary`）—— 和 rust.md 那条「按字节截的样本切在半个字上」同一个坑。
（`HeadTailBuffer` 是按字节存的，中间那道缝可能切在半个字上，转成字符串时会多一个替换符。它在乎的是「总量有界」，这点代价接受了。）

### 4. 长时间跑的命令：先回一段，之后来取

`unified_exec`：命令起来后最少等 250ms、最多 30 秒就先把已有的输出交给模型，附「进程还在跑，会话 id 是 X」；模型之后用这个 id 再来取新的输出、或者往 stdin 写。
输出存在 `HeadTailBuffer` 里：一半预算存开头、一半存最近的结尾（`VecDeque`，旧的从前面丢），丢了多少单独记。同时最多 64 个进程。

这和我们的运行窗是同一类东西（dev server 一跑几小时），只是消费方从人换成了模型。**对 #46 的一个设想（未核实）**：ACP 里有一组「编辑器替 agent 开终端、
取输出、等退出、杀掉」的方法（`terminal/*`），如果要支持，`tasksvc` 现成的进程组、整组停、输出落盘可以直接当它的后端，取输出时用 head + tail 交出去。
第 0 步核实 ACP 这组方法的确切形状。

| ⑨ | #46 拼给模型的东西（报错、日志片段）：截中间、带原始大小、中文别按 4 字节估 token | #46 设计稿 |

## 主题 4：配置分层、会话记录落盘（2026-10-12）

读了：`config/src/config_layer_source.rs`（全读）、`config/src/loader/{mod.rs 的分层说明和信任那段,README.md}`、`app-server/src/config_manager_service.rs` 的写回、
`rollout/src/{recorder,reverse_jsonl_scanner,state_db,writer_lock}.rs` 的注释和读坏行那段。对照我们的 [SETTINGS.md](../SETTINGS.md)、会话快照、`windows.json`、`live.json`。

### 1. 配置九层，每层记着自己从哪来

内置默认 < 企业设备管理（MDM）< 系统 `/etc/codex` < 企业云端 < 用户 `~/.codex/config.toml`（再叠一层 profile）< **项目 `.codex/config.toml`** < 本次的命令行参数 < 两层旧版兼容。
每层带来源（`ConfigLayerSource`）和版本指纹，合并后还能回答「这个键是哪一层定的」（`origins()`）。

我们只有两层（`settings.rs` 的 `DEFS` 默认值 < 你的 `settings.json`），外加一份应用写的 `ui-state.json`。**不需要学它的层数** —— 九层是企业部署和多入口逼出来的，
个人工具没有这些角色。值得记的是「每个值说得出从哪来」：哪天加了项目级配置，界面要能说「这个值来自项目的 .lite-ide/settings.json」，不然用户会以为自己的设置失灵了。

### 2. 项目带来的配置：加载但停用，说清原因 —— 和我们的信任是两种取舍

项目里的 `.codex/config.toml`、钩子、命令规则，项目没被信任时**照样加载、标成停用**，带一句原因（「把这个项目标为可信才会加载项目配置、钩子和命令规则」）。
加载而不是忽略，界面才能说「这里有一份没生效的项目配置」，而不是假装它不存在 —— 我们 Git 受限时「Git 未启用，点开列出哪几条键」是同一个做法。

差别在**信任记的是什么**：

| | Codex | lite-ide（`gitsvc::trust`） |
|---|---|---|
| 记 | 项目路径 | `.git/config` 的内容 |
| 信任之后项目配置变了 | 照样算可信（`git pull` 带进来的新钩子直接生效） | 作废，重新问 |
| 代价 | 一次信任、长期有效，问得少 | 安全，但内容一变就多问一次 |

我们的取舍站得住：会执行命令的配置项，「当时看过的那份」和「现在这份」不是一回事。

**门控的判据是「会不会自动执行」**：它关的是配置、钩子、命令规则 —— 都是不用人点就会跑的。我们的 `.lite-ide/tasks.json` 也是项目带来的命令，但只有你按 ⌃R 才跑、
命令在列表里看得见，所以不需要信任闸。以后加「打开项目时自动做点什么」的功能，就要过同一道闸。

### 3. 改用户的文件：格式决定了贵不贵

它的界面改 `config.toml` 用 `toml_edit`（只改那一个值，注释、空行、键的顺序都在），并且带 `expected_version`（文件指纹）：读的时候记下，写之前比，
中间被人改过就报 `ConfigVersionConflict`，不硬盖 —— 乐观并发，和我们保存文件前比 stamp 一个思路。

我们 SETTINGS.md 3.1 拆成两份文件，理由之一就是「保住注释地改 JSONC 要自己写两三百行的解析器」。Codex 选 TOML、TOML 有现成的保格式编辑库，这条成本就没了。
**选配置文件格式的时候，「程序能不能不破坏格式地改它」是一条要考虑的标准。** 两份文件也有它自己的好处（按钮一天按几十次，不去动你手写的那份），所以不改。

### 4. 会话记录：只追加的事件日志是真相，索引可以重建

- 每个会话一个 `.jsonl`，一行一个事件，**只追加**。一条后台写线程负责写；写失败时没写进去的留在队列里，下一次刷盘时重开文件重试，不丢。
- 列会话、搜会话用 SQLite，但 **SQLite 是从 JSONL 派生的**：启动时补齐，查不到就退回去扫 JSONL 再把索引修好（`state_db.rs` 的 reconcile / backfill）。
- 读的时候**坏一行跳一行**：解析失败记一条警告、计数、接着读（`load_rollout_items`）。崩溃时最后一行只写了半截，丢的只是那半行。
- 跨进程写锁（`writer_lock.rs`），防两个进程往同一个会话里写；旧记录压缩、过期清理。

对照我们：

| | 我们 | 它 |
|---|---|---|
| 存什么 | **快照**（现在开着什么）：会话、`windows.json`、`live.json` | **事件日志**（发生过什么） |
| 坏了 | 整份读不出 → 当没有（`session.parse` 返回 null，启动不受影响） | 坏一行丢一行 |
| 写 | 整份写临时文件再改名（`live.json`）/ localStorage | 追加一行 |

两种都对，看要什么：我们要的只是「上次开着什么」，快照最简单、也最小；它要能回放、从中间某一步分叉、按内容搜，就得是日志。
**通用经验**：数据只有一个真相来源，别的（索引、缓存、摘要）都从它派生、都能重建。派生的东西坏了不可怕，怕的是两份都当真相、互相对不上。

### 对 lite-ide 的行动项

| | 做什么 | 排在哪 |
|---|---|---|
| ⑪ | 以后加项目级配置：每个值说得出来自哪一层；会自动执行的项过信任闸 | 记着，做到时照办 |
| ⑫ | #46 如果要存对话历史：每个会话一个只追加的 JSONL、坏行跳过、索引从它派生（先看 ACP agent 自己存不存 —— 存的话我们不该再存一份） | #46 设计稿 |
| ⑬ | 信任按内容记（我们的做法）维持不变 | 不动 |

## 主题 5：测试和工程组织（2026-10-12）

读了：工作区 `Cargo.toml` 的 `[workspace.lints]`、`clippy.toml`、`deny.toml` 的开头、两份子目录的 `AGENTS.md`、`core/tests/common/context_snapshot.rs`、
`.github/workflows` 的清单。数了 insta 快照和假服务端的用量。

### 1. 规矩交给编译器：`clippy.toml` 的 `disallowed-methods`（最值得学的一条）

它把「这个 API 别直接用，走我们的包装」写成 lint，理由就写在规则里：

```toml
{ path = "sqlx::Pool::connect", reason = "Create SQLite pools through codex-state's sqlite shim." }
```

另外工作区级 `unwrap_used` / `expect_used` / `await_holding_lock` 都是 `deny`（测试里放开）。

**我们有一模一样的规矩，全靠文档**：起子进程走 procutil、`File::create` 会截断、`fs::rename` 会静默覆盖、删用户文件只走废纸篓 —— 都只写在 rust.md 里。
searchsvc 把两个管道的读法写反、造成死锁（2026-10-10），正是「规矩只在文档里」的代价。**我们的 CI 连 clippy 都没跑。**

实测（临时放一个 `clippy.toml`，跑完删了）：这七个 API 在全仓库命中 242 处，其中产品代码 34 处，其余是测试里清理临时目录。
34 处逐个看，大部分是有意的（先写临时文件再改名、清理自己生成的文件、procutil 自己），**但有一处真的违反了规矩**：

> `gitsvc::discard` 丢弃**未跟踪**的文件时直接 `remove_file` / `remove_dir_all`，没走废纸篓。rust.md 写的是「`move_to_trash` 是删用户文件的唯一路径」。
> 确认框说得很诚实（「未跟踪的文件会被直接删除，这一步不可撤销」），所以不是骗人的 bug；但未跟踪的文件 git 里没有任何历史，删了就彻底没了，
> 而放进废纸篓几乎没有代价。删除出错时 `let _ =` 吞掉，界面照样报成功。

**规矩交给工具，第一次跑就抓到一处。** 建议：加 `clippy.toml`（上面那七条），有意为之的地方逐个标 `#[allow(clippy::disallowed_methods)]` 并写一句为什么，
测试文件整体放开；CI 只跑 `cargo clippy -- -A clippy::all -D clippy::disallowed_methods`，**不顺手开全部 clippy**（那会冒出几百条风格警告，和这件事无关）。

### 2. 快照测试：测「变了没有」，不测「对不对」

- insta 快照 **1,559 个、16 个 crate**：TUI 渲染出来的整屏、发给模型的整段上下文，存成文件，变了测试就红，`cargo insta review` 逐个看、接受或拒绝。
- **上下文快照**（`core/tests/common/context_snapshot.rs`）：把真正发给（假）模型的请求截下来，路径、id 这类每次都变的值先规范化掉，渲染成人读得懂的文本。
  「模型看到了什么」一变，代码审查的 diff 里就看得见。

快照测试的强项是**覆盖面**（一次断言整屏），弱点是它只知道「和上次不一样」，不知道「上次那份对不对」，而且改多了容易一路点「全部接受」。
**对 #46**：「我们发给 agent 的东西」（拼进去的选区、报错、文件内容）值得照这个做快照，规范化掉路径。加 insta 是加依赖，要先问。

### 3. 假的对端：120 个测试文件跑在假模型服务端上

`core/tests` 里 120 个文件用 wiremock 起一个假的模型 API，按剧本回话 —— agent 的整个循环（发请求、跑命令、批准、再发）在没有网络、结果确定的条件下端到端地测。
**对 #46**：要一个**脚本化的假 ACP agent**（读 stdin 的 JSON-RPC、按剧本回、能故意不回 / 回慢 / 中途退出），反方向请求、超时、取消、进程收尾都在它上面测。
这和我们的 `mock-ipc` 桩、测试通道是同一个思路：把对端换成可控的，才测得到边界情况。

### 4. 两份子目录的 AGENTS.md：写清「这一阶段故意不做什么」

和我们的 AGENTS.md 一样是写给 agent 的规范，不一样的是它**按目录放**，而且写了一节「刻意的近似」：哪些误报、漏报是这一阶段**接受的限制**、
「不是让你去补的」—— 免得 agent（或者审查的人）把已知的取舍当成 bug 去修，同时说清「哪些回归仍然要修」。
我们 `.claude/rules/*.md` 按改动路径加载，是同一种「规范离代码近」的做法；「已知限制，别去修」这种写法我们还没有，DIRECTION 的「不做」一节最接近。

### 5. CI 里的几样我们没有的

`cargo-deny`（依赖的许可证、已知漏洞、重复版本）、`codespell`（拼写）、`blob-size-policy`（提交里的大文件）、按平台分开的完整测试。
我们只有入口包体积那一道闸（160 KB 红线）。开源前值得补的是 cargo-deny 的许可证和漏洞检查（#47 门面那一档），别的用不上。
