# 日志归类：一百万行归成几十类（2026-10-14）

> 状态：**做完了**（含第 6 节的对比）。Rust 侧 `crates/logengine/src/pattern.rs`（12 条测试，四种错版本各自验过红 —— 第一轮有三种没红，见第 5 节）；
> 前端 `logview/PatternPopup.svelte`、`logview/pattern-query.ts`（14 条）；真 `.app` 验收 `scripts/accept/patterns.sh` 8/8。

## 0. 一句话

打开一份从服务器拉下来的日志，第一个问题往往不是「第几行写了什么」，而是**「这里面都发生了些什么、各多少」**。
级别计数只说得出「有 4 千条 ERROR」，说不出它们是一种错还是四十种。日志视图的过滤条上点「归类」：

```
 ●  8,491  42.5%  INFO [http-nio-<*>-exec-<*>] c.d.Order - 下单 userId=<*> sku=A-<*> qty=<*>
 ●  5,719  28.6%  DEBUG [pool-<*>-thread-<*>] c.d.Cache - evict key=order:<*> ttl=<*>s
 ●  2,900  14.5%  WARN [http-nio-<*>-exec-<*>] c.d.Retry - 重试 attempt=<*>/5 backing off <*>ms
 ●  2,890  14.4%  ERROR [scheduler-<*>] c.d.Order - 订单落库失败 orderId=<*> cause=Deadlock…
```

点一类 = 按它的模板过滤（只看命中 / 全文、F3 跳、高亮都是现成的）。合并视图里一样能用（几份一起归）。

## 1. 算法：Drain，改了两处

Drain（He 等，ICWS 2017）是日志分析里最常用的在线模板挖掘算法，每行近似 O(1)：

1. **切词、把变量换成 `<*>`**
2. **按「词数 + 前两个常量词」分桶** —— 原文是一棵固定深度的前缀树，压平成一个 HashMap 是同一件事
3. **桶里挑最像的那一类，过半就归进去**，模板里对不上的位置变成 `<*>`；没有过半的自立一类

**改动一：变量只换「带数字的那一段」，不换整个词。** 原版把带数字的整个词换掉，`userId=1024` 变成 `<*>`，「userId=」这个信息就没了。
这里按非字母数字再切一层：`userId=1024` → `userId=<*>`，`[http-nio-8080-exec-2]` → `[http-nio-<*>-exec-<*>]`。
常量留下来有两个用处：模板读得懂；拿模板当过滤条件时筛得准（第 3 节）。

**改动二：相似度的分母只数这一行的常量词。** 原版是「一样的词 / 总词数」，模板里的 `<*>` 不算一样 ——
一行里 id、数字一串占了一半以上（`user 1 2 3 4 login`），相似度永远过不了半，每一行自成一类。变量本来就该不一样，不该拿来扣分。

## 2. 归哪些行

带时间戳的文件**只归有时间戳的行**（一条记录的头）：堆栈帧、异常那一行、多行 SQL 是这条记录的附属，自己成类只会淹掉真正的类。
没有时间戳的文件归所有非空行、跳过堆栈帧。几份（合并视图）各自判。

## 3. 点一类 → 过滤条件，不新造「按类号筛」

两条路：

| | 做法 | 代价 |
|---|---|---|
| 按类号筛 | 归类时给每一行记类号，过滤时查表 | 1GB 日志 900 万行 × 4 字节 = 36MB；还要另写一套过滤、和合并视图再对一遍 |
| **模板的常量词当过滤条件**（现在） | `"ERROR" "[scheduler-" "c.d.Order" "订单落库失败" "orderId=" …`，过滤框原来的语法（`query.ts`） | 理论上是**超集**：别的行也可能恰好含着全部这几个词 |

选了第二条：复用现成的过滤、高亮、只看命中 / 全文、F3、合并视图，内存零增加。超集在实测里一条不多（验收脚本那份 2,890 条、浏览器里那份 4,167 条，筛出来都正好是那一类的次数）。
最多取六个最长的常量词，**按词取、不按整段取** —— 模板是切词后用单个空格拼回去的，Logback 把级别补成五格（`INFO  [`），整段加引号的 `"INFO [http-nio-"` 在原行里对不上（第一版的测试拿 `replace("  ", " ")` 把这个盖住了，第 5 节）。

## 4. 实测

`gen_log` 造的三份 Java 日志，144MB、128.6 万行（M 系列，`--release`，`examples/bench_pattern.rs`）：

| | 数 |
|---|---|
| 归类 | **386 ms**（0.36 GB/s），后台线程里跑，每 26 万行发布一次快照（边归边看） |
| 结果 | 128.6 万行 → **4 类**，正好是生成器的四种消息；120 行堆栈不算记录 |
| 按 1GB 推 | 约 3 秒，进度在状态栏 |

## 5. 测试是怎么被打脸的（值得记）

第一轮写完 9 条全绿，拿四种「真会写出来的错」去验，**三种没红**：

| 错版本 | 为什么没红 | 补了什么 |
|---|---|---|
| 相似度改回原版 | 测它的那条用的是时间戳的例子 —— 按段归一之后 `2026-08-24` 是 `<*>-<*>-<*>`，形状本身是常量、照样对得上，原版也能过 | 换成整词变量占一半以上的例子（`user 1 2 3 4 login`） |
| 带时间戳的文件也归续行 | 例子里的续行全是 `\tat …` 栈帧，被另一条规矩（跳过栈帧）挡住了 | 加一行不是栈帧的异常行（`java.lang.IllegalStateException: …`） |
| 先判上限再找已有的类 | 第一版造的「错」是一句什么都不改的 `let _ = 0;` | 换成真的把判上限挪到最前面 |

还有一条反方向的：「过半就归」那条测试第一版红了 —— 是**期望写错了**：「shipped to carol」和「paid by」只对得上两个常量词，本来就该自立一类。
另外，前端 `pattern-query` 的第一版测试为了让原行能匹配，把原行里的两个空格替换成一个 —— 这一下替算法盖住了一个真 bug（第 3 节）。
**测试里对输入做的任何「顺手处理」，都要问一句它是不是在替被测代码干活。**

## 6. 对比：和昨天的、上线前的那份比（同日下一轮做的）

归类浮层的脚栏「和另一份比…」选基准（可以多选），每一类说**新出现 / 没了 / ×8 / ÷3 / 持平**，基准次数 → 这一份次数：

```
 ●  新出现     0 → 2,890   ERROR [scheduler-<*>] c.d.Order - 订单落库失败 orderId=<*> …
 ●  没了   2,474 → 0       INFO [scheduler-<*>] c.d.Health - healthz ok upstream=<*>
 ●  ÷1.7   2,522 → 2,900   WARN [http-nio-<*>-exec-<*>] c.d.Retry - 重试 attempt=<*>/5 …
```

**「同一类」怎么认：两边放进同一个 Drain 里一起归，每一类分两边计数。** 排除的路是「两边各归一遍、再按模板文字去配」——
同一句日志在两次归类里可能长成不一样的模板（这边某个位置成了 `<*>`、那边没有），按文字配不上，同一类被当成「一边新出现、一边没了」。
放在一棵树里，「是不是同一类」只判一次。验红时把基准那边换成单独一个 Drain，两条对比测试都红。

**按频率比，不按次数比**：频率 = 这一类的次数 / 那边一共归了多少行。今天的日志比昨天长一倍，每一类次数都翻倍，那不是变化。
排序三档（Rust `change_rank`）：新出现 → 没了 → 两边都有的按变化幅度（涨几倍和跌到几分之一取大的，所以 ×8 和 ÷8 一样靠前），幅度一样看次数。
±50% 以内说「持平」：两天的日志不会一模一样，业务量的起伏不该标出来。点「没了」的那类不筛（这一份里一条都没有），说一句为什么。

## 7. 没做的

| | 为什么 |
|---|---|
| 每类的时间分布（迷你柱状图） | 要给每一行记类号或者再扫一遍，等真有需要 |
| 类的上限 2 万 | 乱到这个地步，分再多也没用；超出的行界面上照实说「还有 N 条没归进去」 |
| tail 时自动跟着归 | 面板上有「重新归类」。边长边归要处理「已经归过的那段」，等真有人要 |
