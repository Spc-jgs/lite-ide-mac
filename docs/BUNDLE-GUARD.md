# 入口门禁与按需加载

2026-10-30 调研与实施。结论：保留按需加载的主要边界，保留入口 152/160 KiB 预警/红线作为当前项目的回归线；修正计量精度、补完整静态依赖总量保护。**没有足够的当前启动分布证据把 160 KiB 认定为最优性能上限，也不以 Vite 默认警告线直接替换它。**

## 1. 为什么原门禁需要修

旧 CI 只从 HTML 取第一个 JS 文件，`size / 1024` 取整后才比较 `>160` / `>152`：实际硬线会放行到 164863 B，预警要到 156672 B 才出现。配置写“KB”，计算却是 KiB；静态 helper/vendor 文件还可能被遗漏。把大模块挪到另一个静态 chunk 能改变单文件体积，却没有减少启动需要解析的代码。

历史数值来自本项目的迭代：2026-09-03 拆掉误进入口的语言加载表与 Tauri webview API 后收紧；09-14 组件/状态拆分增加必要接线，调整预警；09-21 复核可拆边界后改为 145/160；10-12 对源码映射与实际构建做差，新增设置/运行状态等必要接线约 7.4 KB，预警从 145 调到 152、硬线 160 未变。旧归因账见 [c94e4ae 时的前端规则](https://github.com/Spc-jgs/lite-ide-mac/blob/c94e4ae9046ab7bfe9c362d3352c635f53c02102/.claude/rules/frontend.md#重的东西一律按需加载) 和 JOURNAL；这些是历史证据，不是今天的启动占比。

本次改成 `scripts/bundle-budget.mjs`，本地与 CI 复用：

| 指标 | 当前动作 | 依据 |
|---|---|---|
| 入口文件未压缩字节 | >155648 B（152 KiB）预警，>163840 B（160 KiB）失败 | 延续原项目决策，修复取整偏差；不是行业标准 |
| 入口 + 递归静态 JS 依赖总量 | >165888 B（162 KiB）失败 | 当前额外只有 1110 B 的 Vite helper，在原入口线上留 2 KiB 构建支持余量；卡总量以拦住静态 vendor 绕过，同量代码移到共享块仍允许。新口径保守保护线，不是运行时卡顿阈值 |
| 各静态依赖明细 | 报告并去重 | 递归走 manifest `imports`，不走 `dynamicImports`；本项目预期一个 HTML/JS 入口，新增入口需重审口径 |
| 静态 CSS、全部 JS 数量/体积、gzip | 报告，不套入口红线 | CSS 有样式处理成本；全部 JS 包含未使用的功能，gzip 仅参考，不能冒充解析执行成本或 Tauri 实际传输量 |
| 缺 manifest、缺静态依赖/文件 | 失败 | 缺失不能记成 0 或误报通过 |

160 KiB 几乎没有剩余空间，预警不是“请压缩几句文案”的指令。下一次合理功能增量碰线，应读构建依赖/归因、确认加载必要性、测同机同会话的启动与首次操作，再决定结构调整还是修订数值；保留证据。复核时曾考虑把额外静态块单独卡 2 KiB，但这会让“同量代码从入口移到共享块”误失败，因此最终卡总量，新增回归。若合理改动需要超过总线，仍按同样过程审，不为过线切碎模块。它们是发现变化的工具，不能替代用户体验验收。

## 2. 当前构建量到什么

基于 `c94e4ae` 的应用实现，本次不改产品功能/加载逻辑。实际依赖为 Vite 6.4.3、Svelte 5.56.10、Tauri JS API 2.11.1。正式配置 `safari15`、esbuild minify，未升级依赖。带 manifest、**不带 sourcemap** 的生产构建：

| 项目 | 字节 / 数量 |
|---|---:|
| 入口 JS | 163548 B（159.71 KiB）；离入口红线 292 B |
| Vite preload helper（递归静态依赖） | 1110 B |
| 入口静态 JS 合计 | 164658 B（160.80 KiB） |
| 上述 JS 分文件 gzip 后合计 | 60519 B（仅参考） |
| 入口静态 CSS | 29567 B |
| 全部产物 JS | 2766232 B / 211 块；不等于启动执行了这些代码 |
| 源码中明确的立即/300ms 预拉根节点 + 静态依赖并集 | 310317 B / 31 块，含入口；是静态下界，不是完整运行时加载量/执行耗时 |

便携证据见 [bundle-audit-2026-10-30.json](research/bundle-audit-2026-10-30.json)，有构建产物 SHA、口径、依赖与源码触发位置。分析 sourcemap 的另一轮入口为 163591 B；多出的 sourceMappingURL 会改变产物体积和文件名，不混作正式基线。

本机源码映射按生成段归属的候选排序：App 约 14.7 KB、StatusBar 约 8.1 KB、Content 约 7.2 KB，其余分布在 Svelte 运行时、标签/文档/会话/设置等共享状态，没有发现 CodeMirror/xterm 主实现静态进入口。归因可能把相邻生成代码计入同一个源文件，只用于查候选，不能相加当移走后的收益。错误屏、保存/恢复保护和跨组件状态有首屏职责，当前不为省几十字节另建宿主或转发层。

## 3. 懒加载是否合适

“动态 import”是构建边界，“调用 loader 的时机”才决定何时请求/执行。代码文件名出现在预加载表中，也不代表所有文件已请求。

| 组 | 当前触发 / 额外静态 JS 闭包（相对初始入口去重） | 判断与代价 |
|---|---|---|
| 编辑器 + CodeMirror | 显示编辑标签才加载；493359 B | 保留。日志用户不用支付整套编辑器成本；恢复编辑会话会在启动期间加载，属于该场景的真实启动成本 |
| 终端 + xterm | 有终端并显示/恢复对应组件；375289 B | 保留。恢复终端时同样不能排除在启动测量外 |
| 日志视图 | 日志标签/运行输出使用时；51248 B | 保留。和编辑器对称，不给只写代码的人默认加载 |
| 文件树 | App 挂载时立即请求；35864 B | 保留当前方案。拆包能与列目录 IPC 并行，但不是“完全不参与启动” |
| 搜索/跳行、确认框、右键菜单、菜单动作、底部面板壳 | 大多挂载约 300ms 后预拉；面板壳自身新增静态闭包 32839 B | 为常用第一下操作减少等待，当前有明确用途。300ms 是相对挂载，不保证首屏已画完；慢恢复时可能重叠。没有量到首次操作收益/CPU突发前，不扩大预拉，也不贸然删掉全部预拉 |
| Git 详细视图 | 打开 Git 侧栏、diff/merge、日志或分支时触发一组 | 基本合理；历史/分支一起拉是取舍。首次只看一份 diff 时可能多拉其他视图，若出现等待/内存信号，再测分组收益，不先拆五套句柄 |
| Maven、Gradle、结构、数据库、AI | SideToolHost 按工具窗再加载具体组件 | 保留。Maven/Gradle/DB 视图额外静态闭包约 27/20/23 KB，重工具的启动仍另看 Rust/子进程，不能只看 JS。AI 继续按用户决定暂缓 |
| 语言实现、Java/LSP、HTTP/SQL编辑扩展、重构弹窗 | 跟随对应文件/操作 | 保留。语法识别表和语言实现分别加载，真实项目导入/JVM 内存不能由 bundle 数字背书 |
| 更新提示、旧任务/替换现场检查 | 挂载/项目变化后约 1.5s | 不是纯交互按需：承担更新检查/恢复职责。保留现有触发，CPU/网络/资源另按清单验收 |

预拉根节点来自 App 的 FileTree、Confirms、ContextMenu、Panel、menu-actions，以及 Overlays 的 QuickSearch/Outline/GotoLine/keymap；并集已去重，不能把各功能增量相加。还没包括所有 1.5s 工作、欢迎/恢复场景和用户操作触发，因此 310317 B 不是“完整启动 JS 预算”。

## 4. 官方资料与适用范围

通过 Context7 核对 Vite、Tauri、Svelte 官方资料，并读本机 Vite 6.4.3 的类型与实现：

- [Vite manifest](https://vite.dev/guide/backend-integration)：`imports` 和 `dynamicImports` 分开描述；共享依赖要递归、去重。
- [Vite 异步分块预加载](https://vite.dev/guide/features#async-chunk-loading-optimization)：动态 import 触发时并行拉共享依赖，预加载文件名表不等于启动时无条件加载全部。
- [Vite build 配置](https://vite.dev/config/build-options#build-chunksizewarninglimit)：chunk 警告面向体积；本机 Vite 6 的默认 500 kB 是单块警告，不是桌面首屏建议值。本机实现按未压缩 chunk 计算，gzip 另外报告。当前网站面向更高主版本，涉及版本细节以锁定安装版本源码核对，不照搬新版 Rolldown 配置。
- [Tauri 进程模型](https://v2.tauri.app/concept/process-model/) 与[前端配置](https://v2.tauri.app/start/frontend/)：应用内嵌本地前端，macOS 使用系统 WKWebView；网站的网络传输预算不能原样套成此项目的硬线，JS 解析/执行、样式和恢复工作仍需要量。
- [Svelte 动态组件导入](https://svelte.dev/docs/svelte/await)：可以按功能加载；没有给此项目规定 160 KiB 上限。

没有查到适用于所有 Tauri/Svelte 桌面应用的统一入口字节红线。项目应把体积保护、功能首次操作、启动与资源测量合用；不能声称“现代编译器会自动决定最佳加载时机”。

## 5. 后续怎样复查

```bash
pnpm bundle:check
# 默认正式应用构建不额外携带审计 manifest；CI 构建时加 --manifest 再跑同一检查器
pnpm build --manifest
node scripts/bundle-budget.mjs dist
```

本地 bundle:check 使用 `src-tauri/target/bundle-budget.noindex/dist`，不覆盖正常 dist；要留 JSON 可给检查器第二个位置参数指定输出文件。归因调查可在单独目录加 `--sourcemap`，它只用于找候选；正式门禁基线使用无 map 构建。

本轮资源清单登记：R01 构建/方法身份、R20 体积/正式包、R21 静态加载边界已查；R08 当前启动分布仍 UNKNOWN。对隔离测试应用读 Resource Timing：空窗与打开文本后均返回 0 个条目，不能据此声称没有加载文件；测试页 `hidden=true`，因此没有把后台计时包装成前台首屏/首次操作延迟，也没有使用真实数据/全局按键。应用实现未改，仅构建门禁/维护规则变化，R02–R06 的资源循环、R09–R19 的专项及 R22 长测本轮不重跑：相关运行行为未改；原有调查不升级为通过。后续资源复测因 package.json 构建身份变化须先 `--build`。

下一次要决定调高/调低数值或改预拉行为，优先补：同机的空窗/日志/恢复编辑器/恢复终端四场景，区分打包后首次与后续启动，记录分布和主线程耗时；再测首次搜索、切标签、开面板的反馈/完成延迟以及 0–2s 总工作量。需要占用前台的步骤先核对授权。不能再用 2026-09-18 的 57ms/14% 当当前占比。
