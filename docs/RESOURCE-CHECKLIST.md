# 项目资源与性能检查清单

本清单是持续使用的验收入口，包含已测正常项、已修复后的回归项和待测项。相关代码变化后，历史正常项仍要复测。由人提出检查，或 agent 依据改动触发；每轮执行后退出。

2026-10-30 建表。现有资源证据主要来自单窗口、后台、无 JVM 的隔离测试；前台响应、大型 Java 项目和长期资源占用另列。方法、调查线和历史数字以 [RESOURCE-GUARD.md](RESOURCE-GUARD.md) 为准，功能验收入口以 [AGENTS.md](../AGENTS.md) 为准。

## 1. 每轮怎样使用

1. 明确本轮改动/现象、应用构建、测试场景与测试身份。先检查 R01。
2. 资源检查常规覆盖 R02–R06、R20；根据表中触发条件选其余项。对总表逐行标注“本次检查 / 不适用 / 暂缓及原因”，保证经过选择，不要求每次执行全部重型专项。
3. 执行选中的场景。已有正常记录可作匹配场景的基线，不能替代本次测量；功能测试通过与资源通过分别记录。
4. 按第 4 节留记录，更新本表的最近证据和对应 issue。告警复核条件并定向复测；仍有缺失就保留 UNKNOWN。

状态含义：**本场景未见异常**仅指证据覆盖的范围；**调查中**有信号但原因未定；**待测**尚无对应资源证据；**仅功能入口**已有可复用验收，但没有同步测资源。修复项保留在表中作为回归项。

## 3. 执行入口

**A · 普通资源回归**（R01–R06 的单窗口基础场景）：

```bash
scripts/resources.sh --self-test
scripts/resources.sh --build --profile quick
# 应用源码/测试构建未变时省略 --build；有增长或改生命周期再选 full
scripts/resources.sh --profile full --pace paced
scripts/resources.sh compare /path/to/before/report.json /path/to/after/report.json
```

**B · 内存定位**（R03/R21）：

```bash
scripts/resources.sh --profile full --pace paced --inspect-lifetimes
scripts/resources.sh --profile full --pace paced --inspect-lifetimes --control ipc
scripts/accept/minimap.sh
scripts/resources.sh --workload logs --profile quick --log-mib 64
scripts/resources.sh --workload logs --profile quick --log-mib 1024 --native-diagnostics
```

弱引用探针只注入测试页面，跟踪观察到的 EditorView、doc 和新建 canvas，只保存弱引用、不请求 GC。默认 `--lifetime-sampling final` 在恢复空闲末尾只解引用一次；需要时用 `--lifetime-sampling checkpoints` 做分阶段观测对照。解引用会短暂保活目标，观察时点是测量方法的一部分，两种模式不能混作收益比较。对象仍 alive 可以是尚未 GC，不能直接判泄漏；cleared 可以排除这些具体对象继续存活。canvas 的对象存活、是否连在 DOM、位图是否非零分开计数，不把像素数当物理内存。观测不覆盖所有 JS/native 对象，必要时再做分配/引用来源定位。规范依据：[ECMAScript WeakRef](https://tc39.es/ecma262/multipage/managing-memory.html#sec-weakref-objects)。

IPC 对照在 opened-* 阶段保持相同调用位置与等待节奏，但不打开编辑器；报告记录外部 eval 实际次数（不是全部业务 IPC）。结束后仍实际打开/过滤日志，可观察没有编辑器使用历史的日志场景。两种诊断都改变 scenario，不能与普通轮次算收益；日志发生在 IPC 之后，不冒充全新的、未做其他操作的进程。

**C · 构建与规则验证**：应用代码改动按 AGENTS 执行 `pnpm check`、相关测试与 `pnpm app:bundle`；Rust 改动选择 workspace 测试和 clippy。仅文档改动可说明原因跳过构建。构建/验收与资源采样串行，避免相互干扰。

**D · 专项入口的使用**：总表中的 `.sh` 均位于 `scripts/accept/`。先读对应脚本和领域文档，在已有隔离 fixture 中加上启动前/使用中/停止后/退出后的资源采样；直接跑功能脚本，只能记录功能结果。没有现成资源包装的项明确记待补，不能把命令存在当测量完成。测试身份串行使用，本机工具/镜像缺失就记 UNKNOWN。

R07、R08 的前台测量、真实休眠/网络卷、热状态与能耗专项，先确定可用能力和已有授权；需要打断前台而未获授权时，保留待测并完成其他可独立检查的项。构造磁盘满/只读/断网只限自有临时 fixture，真实项目和系统环境不用于故障实验。

## 4. 每轮记录模板

复制以下内容写入当轮报告；原始 report.json/md 留在工具给出的目录，公开 issue 只写仓库相对位置和必要数值。

```markdown
日期 / 执行者 / 触发原因：
构建：HEAD、dirty、源码 SHA、二进制 SHA、测量方法/诊断脚本版本
环境：机器/OS、前后台、电源条件、内存压力前后；进程归属是否完整
本次覆盖：Rxx、Rxx
其余条目：逐项写不适用或暂缓理由（不得留空冒充全部检查）
命令 / fixture规模 / 操作节奏 / 预热 / 时长 / 退出码：
资源结果：阶段、实数、单位、趋势与异常
功能测试结果：实际条数、失败、跳过；与资源结果分开
结论：NO_SIGNAL / REVIEW / FAIL / INVALID；缺失指标写 UNKNOWN 并说明
复测及比较：条件是否相同；不可比的原因
遗留资源/临时文件、issue、下一次触发检查的条件：
```

结果更新遵循：正常项保留回归入口；已修复项保留复现/验红及复测证据；观察项有新证据再提升优先级。所有选中项都必须有实测结果或明确的未完成原因，不能只更新“总体通过”。
