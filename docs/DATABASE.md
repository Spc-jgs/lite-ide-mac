## 1. 要什么、不要什么

取代 IDEA 的 Database 工具窗里**天天用的那一半**：

| 要 | 不要（这一版） |
|---|---|
| 连接管理（MySQL、PostgreSQL 起步；H2 / SQLite 给验收和本地开发用） | 表结构的图形化设计器（改表走 SQL） |
| 库 → 表 → 列 / 索引的树（懒加载） | ER 图、数据对比、迁移 |
| SQL 控制台：⌘↵ 跑光标所在的那条、历史、取消 | 存储过程调试 |
| 结果表格：几十万行不卡（分批取、虚拟滚动）、复制成 TSV / CSV / INSERT | Redis、MongoDB（另算，不在这一期） |
| 改单元格 → 先给你看要执行的 UPDATE，点了才执行 | 自动提交以外的事务界面（先做「手动提交」一个开关） |
| 导出结果 / 整张表（CSV、JSON、INSERT，边取边写盘） | |
| SQL 里的表名、列名补全（取元数据缓存） | Java 字符串 / MyBatis XML 里的 SQL 补全（第 6 节，后做） |

判据还是 DIRECTION 那句：**秒开不等、独立进程可关、正式包不变大**。数据库客户端不打开就一个字节不加载。

## 2. 驱动怎么带：比了三条路

| | A. JDBC，跑在内置的 Java 21 上（边车进程） | B. Rust 的驱动（sqlx / tokio-postgres / mysql_async） | C. 起 `mysql` / `psql` 命令行、解析输出 |
|---|---|---|---|
| 能连什么 | 所有有 JDBC 驱动的（MySQL、PG、Oracle、SQL Server、H2、达梦、OceanBase……）—— IDEA、DBeaver 都是这条路 | 每种库一个 crate；Oracle / SQL Server 基本没有能用的 | 装了哪个命令行连哪个 |
| 类型 | JDBC 的类型系统，`getObject` + 元数据，和 IDEA 看到的一样 | 每个 crate 各一套，DECIMAL / 时区 / JSON 各写一遍 | 全是字符串，NULL 和空串分不清 |
| 正式包 | **不变**：Java 21 运行时已经在包里（jdtls 用的）；驱动按需下（MySQL Connector/J 是 GPL，本来就不能打进包） | 变大：每种驱动 + TLS（rustls 一套就 1–2 MB） | 不变 |
| 启动 | 第一次开数据库工具窗起一个 JVM，约 0.3–0.6 秒（量过 jdtls 的冷启动 JVM 本身 0.2 秒）；闲 10 分钟收掉 | 0 | 每条 SQL 起一次进程 |
| 内存 | 边车 ~60–80 MB，只在用时 | 几 MB | 0 |
| 取消、流式 | `Statement.cancel()`、`setFetchSize` 分批 | 各 crate 不一样 | 杀进程 |

**选 A**。理由三条：能连的范围（国内 Java 后端会碰到 Oracle、达梦、OceanBase，只有 JDBC 有）；类型和 IDEA 一致（同一条 SQL 在两边看到同样的值）；
正式包不变大 —— Java 21 已经在包里，驱动按需下。代价是一个边车进程，和 jdtls 同一种形状（`lspsvc` 那套：进程组、stdin 说话、空闲收掉、`release_window` 收尸）。

**C 不选**：NULL 和空串分不清、类型全丢，这在看数据时是会骗人的。**B 不选**：Oracle / 国产库没有，正式包变大。

推翻它的条件：如果边车的冷启动实测超过 1 秒、或者常驻内存压不到 100 MB 以下，就退回 B、只做 MySQL / PG。

## 3. 边车长什么样

```text
lite-ide (Rust)                         lite-db.jar（Java 21，打包时用内置的 JDK 编，同 hotswap 的 agent）
  dbsvc crate ── stdin/stdout ──────────▶ 一行一条 JSON：{id, op, args}
    · 起 / 停 / 空闲收                        connect / meta / query / fetch / cancel / execute / close
    · 每条请求等多久（连接 10 秒，查询不设）    结果分批回：列定义一次，行每批 500，带「还有没有」
    · 输出设闸（单条消息 16 MB）
```

- **驱动**：`~/Library/Application Support/<id>/jdbc/` 下，第一次连某种库时从 Maven Central 下钉死的版本、核 sha256（同 JaCoCo，D10）。说清下的是什么、多大、什么许可证（MySQL Connector/J 是 GPL：下到你机器上自用没问题，不能打进我们的包）
- **一个连接一个 JDBC Connection**，边车里的线程按连接分，一条查询能单独 `cancel`
- **结果不全取**：`setFetchSize(500)`，界面滚到底再要下一批；导出是边车直接写文件（不经过 IPC，几百万行也不撑内存）
- **超时**：连接 10 秒；查询不设（同 git fetch：靠取消，不靠超时 —— 慢查询本来就要等）

## 4. 连接、密码、存在哪

- 连接的配置（主机、端口、库、用户、驱动、颜色标记）存在**应用数据目录**里、按项目一份（同运行配置，「不往项目里写」）
- **密码进钥匙串**：`security add-generic-password -s lite-ide.db -a <连接 id> -w`（系统自带的命令行，不加依赖），连的时候 `find-generic-password -w` 取。
  不写进任何文件、不过 IPC 回前端
- **从 IDEA 导入**：项目里有 `.idea/dataSources.xml` 就列出来、一键导入主机 / 端口 / 库 / 用户（同运行配置从 workspace.xml 导入）。IDEA 的密码在它自己的钥匙串条目里，不去读 —— 第一次连时问你一次
- **生产库标记**：连接可以标成「生产」（标题栏那一格变红）；生产库上 UPDATE / DELETE 先弹对话框说影响几行（先 `SELECT COUNT(*)` 同条件），不带 WHERE 的直接拦下要你确认

## 5. 界面放哪（照 IDEA，连层级一起抄）

- **数据库工具窗**（侧边栏一个视图，同 Maven / Gradle 工具窗）：连接 → 库 / schema → 表 / 视图 → 列 / 索引 / 外键，懒加载，⇧⇧ 能搜表名
- **SQL 控制台**：每个连接一份 `.sql` 文件（应用数据目录里，同草稿），就是普通的编辑器标签 —— 语法高亮、多光标、本地历史全是现成的。⌘↵ 跑光标所在的那条（按 `;` 和空行分）、选中了就跑选中的
- **结果**：底部工具窗一个「数据库」页（同运行窗），一条 SQL 一个结果标签；表格用日志视图那套虚拟滚动（几十万行只画看得见的）。改单元格只在有主键时允许，改完先列出要执行的 UPDATE、点了才执行
- **历史**：每个连接执行过的 SQL（最近 1000 条，带耗时和影响行数），⌘E 那种浮层里搜

## 6.5 第 0 步实测（2026-10-27）：数字过线，走 A

在 `.app` 里那份裁过的 Java 21 运行时上跑（它带着 `java.sql`，不用另加模块）。驱动：H2 2.3.232，从 Maven Central 下、sha1 和 Central 给的一致
（`4fcc05d9…`，本地算的 sha256 `8dae62d2…`），2.6 MB，MPL 2.0 / EPL 1.0。探针是一个小 Java 程序，外面的 Python 从起进程开始掐表，三次取中：

| | 默认参数 | `-XX:+UseSerialGC -XX:TieredStopAtLevel=1 -Xmx256m` |
|---|---|---|
| 起进程 → 能说话 | 45 ms | 44 ms |
| 加载驱动 + 连上（内存库） | 83 ms | 75 ms |
| 10 万行的表，`fetchSize 500` 取第一批 | 25 ms | 17 ms |
| 全部 10 万行取完（每格 `getObject`） | 63 ms | 35 ms |
| 常驻：刚起来 / 连上之后 | 42 / 74 MB | 37 / 64 MB |

第 2 节写的换路条件是「冷启动超过 1 秒、或者常驻压不到 100 MB 以下」：冷启动 45 ms、连上之后 64 MB，**走 A**，参数用右边那一列（边车不跑长计算，C1 就够；
串行 GC 省一个 GC 线程池的内存）。H2 的内存库把数据放在边车自己的堆里（插完 10 万行常驻到 150 MB），那是 H2 的事 —— 连 MySQL / PG 时数据在服务器上，
边车只攥着当前这一批。没量的：MySQL / PG 驱动的加载时间（本机没有服务器：只有 mysql 命令行和 Docker），DB-1 验收时有就量、没有记「未验」。

## 6.6 DB-2 做成什么样、量到的数（2026-10-27）

db.sh 第二段（H2 内存库，测试身份的 `.app`）：

| | 量到 | 线 |
|---|---|---|
| ⌘↵ 到十万行的表画出第一屏 | **41 ms** | 300 ms |
| 页面里的行元素 | 16 个（取到 500 行时） | — |
| 十万行取完 | 再取 196 批、311 ms | 不卡 |
| 点取消到停下（含测试通道往返） | **321 ms**（边车里 `Statement.cancel()` 本身 1 ms） | 1 秒 |
| 取完十万行之后边车常驻 | 176 MB（H2 的内存库数据也在这个堆里；连 MySQL / PG 时数据在服务器上） | — |

定下来的几件事，连同理由：

- **一个连接最多一个开着的游标**：新查询先关掉上一个。结果标签可以有很多，但每个开着的游标在 MySQL / PG 那边都攥着资源（PG 为了分批取还开着事务）。
  被顶掉的旧结果照旧看得见已经取到的，工具条说「结果集已关闭，重新运行以读取其余行」
- **同一个连接上有一条在跑，就不发第二条**（说一句）：JDBC 的连接不能两条语句同时用，边车会把前一条关掉、它以一句莫名其妙的错收场
- **再执行换掉同一连接没钉住的旧标签**（同 DataGrip）：控制台里改一改再 ⌘↵ 是常态，一次一个新标签很快就是几十个；要留的钉住
- **格子一律是字符串**：BIGINT、DECIMAL 过 JSON 到 JavaScript 会丢精度（`12345678901234567890` 变成 `12345678901234567000`）；NULL 是 null，和空串分开画
- **MySQL 加 `useCursorFetch=true`**：不加的话 Connector/J 把整个结果读进内存才给第一行，`setFetchSize` 不生效；**PG 只读语句临时关自动提交**：PG 只在事务里按 fetchSize 分批。
  关游标时**提交不回滚** —— `WITH x AS (DELETE …) SELECT` 也是 WITH 开头，回滚会悄悄撤掉人家要做的删除
- **一批最多 500 行或 4 MB 字**，一格最多 10,000 字（后面写「共 N 字符」）：单条消息 Rust 那头设了闸，一行几十列长文本时 500 行会过线
- **控制台自己存**（同草稿的自动保存，`project.autosaves`），但不是草稿：标签名是连接名、不收进草稿本、空了也不删。只认应用数据目录底下的（`project.dbConsole`）

已知的不足：MySQL / PG 没有本机服务器，`useCursorFetch` 和 PG 的分批没有实测过；切语句时单引号里的反斜杠按 MySQL 的规矩当转义 —— PG 的 `'C:\'` 这种以反斜杠结尾的字符串会切错（少见，记着）。

## 6.7 DB-3 前一半：生产库保护、导出（2026-10-27）

**执行前确认**（`db/sql-guard.ts` + `DbConfirm.svelte`）：连接可以勾「生产环境」（树里名字后面一个红的「生产」、控制台顶上那条整条染红）。

| | 生产库 | 别的库 |
|---|---|---|
| 只读（SELECT / WITH … SELECT / SHOW / EXPLAIN） | 不问 | 不问 |
| UPDATE / DELETE 带 WHERE | 问，先数会动几行 | 不问 |
| UPDATE / DELETE 不带 WHERE | 问，红字「将删除 x 中的全部 N 行」 | 问（同 IDEA 默认开着的那条） |
| INSERT、DDL、不认识的（CALL …） | 问 | 不问 |

只认最外层：子查询里的 WHERE 不算（`UPDATE t SET a = (SELECT … WHERE …)` 改的是整张表），注释、字符串里的词不算。
数行数是把 UPDATE / DELETE 改写成 `SELECT COUNT(*) FROM 表 WHERE 原条件`，3 秒内数不出来就说数不出来；**多表、带 LIMIT、USING 的不硬数**（按条件数出来的不是会改的那些），说「无法预先统计」。
默认按钮是「取消」，答取消就一条都不跑（同一批里排在前面的 SELECT 也不跑，不留半截）。生产库的结果「重新运行」照样过确认。

**导出**：CSV（RFC 4180、NULL 是空）/ JSON（一行一个对象、NULL 是 null）/ INSERT（表名取语句里的 FROM）。导出的是**整条查询的全部结果**，不是取到界面上的那几批 ——
边车把这条 SQL 再跑一遍、直接写 `<文件>.part`、写完改名过去；取消、出错时删掉 `.part`，保存面板里确认过覆盖的那个原文件不动。进度在状态栏的进度格，那一格的取消就是停。
导出不占「一个连接一个游标」那个位置：正看着的结果导出完照样能往下滚。

量到的（db.sh，H2）：一百万行导出 591 ms、22 MB，边车 180 → 183 MB；导出到一半取消，原来的文件一个字节没动。
**探针撞出来的一条**：H2 默认把整个结果算进内存才给第一行 —— 第一版导出一百万行边车涨到 268 MB，十万乘十万的交叉连接直接把堆撑爆、连内存库一起关了。
连 H2 时加 `LAZY_QUERY_EXECUTION=TRUE`（同 MySQL 要 `useCursorFetch`）之后一百万行 127 MB、三百万行 129 MB —— 不随行数涨。

## 6.8 改单元格（2026-10-27）

双击一格就地改（↵ 攒下、Esc 不改、点别处也攒下、「NULL」设成 NULL），攒下的格子带底色、悬停说原值；「提交…」先列出要执行的 UPDATE（`DbApply`），点了才执行。

- **只有单表、主键全在结果里才让改**（同 IDEA）：边车按 `ResultSetMetaData.getTableName` 判每一列来自哪张表，多表、计算列不让改，没主键（或主键不在结果里）也不让改 —— 双击时说清为什么。
  列标签可能是别名，SET 用列在表里的真名（`getColumnName`）
- **一个事务、每条正好改 1 行**：0 行 = 这行已经被别人改了主键或者删了；多于 1 行 = 「主键」其实不唯一。两种都整笔回滚、改动留着、说是第几条
- **定位用原来的主键值**：主键那一格也改了的话，WHERE 还得指向改之前那一行
- **参数化执行**：值不拼进 SQL（单引号、反斜杠、换行都不用转义）；对话框里那份是等价的写法，好让人对着看。PostgreSQL 加 `stringtype=unspecified`（`setString` 默认按 varchar 发，往 integer 列里写会报类型不符）—— 没连过真 PG 验
- 提交会先关掉这个连接开着的游标（PG 分批取的事务要先提交掉），同一连接上的结果都取不了下一批了，工具条照实说

db.sh（H2）：改值、设 NULL、库里真改了；钉住的结果背后被删了一行、再提交两格：第 2 条改 0 行 → 整笔回滚、第 1 行没动、改动还攒着；有计算列的结果双击不进编辑。

## 6.9 表名、列名补全（2026-10-27）

打开控制台时在后台取一次当前库的表和列（边车一次 `getColumns(catalog, null, %, %)`：一张表一次的话几百张表就是几百个来回；H2 上 7 ms），
系统库不收（H2 的 INFORMATION_SCHEMA 一个就几百列）、最多 5 万列，多了照实说「补全：前 N 列」。补全本身是 lang-sql 的 `schemaCompletionSource`：`schema.表`、`表.列`、别名（`o.` 认出 o 是哪张表）都认。

- **默认 schema**：不写前缀时补哪个 schema 的表。连接默认的那个里没有表（H2 默认 PUBLIC、表全建在别的 schema 里）而有表的只有一个，就用那一个 —— lang-sql 给一个没表的 schema 当默认，不写前缀就一个表名都补不出来（读过 `CompletionLevel.child`）
- **控制台里执行成功一条 DDL 就重取**：刚建的表马上补得出来（db.sh 验过；把重取那句去掉，这条当场红）
- 控制台顶上说读到了几张表；取不到就说取不到、为什么

已知的：`o.` 之后 lang-sql 的关键字补全照样混在列名后面（列名排在第一个）；结构是打开时那一刻的，别处改了表（不是在这个控制台里）要重开控制台。

## 7. 和现有东西的接口

- 进程纪律：`dbsvc` 照 `lspsvc` 的形状（rust.md「起子进程的三条硬纪律」：stdin 是说话的管道，单条消息设闸，读线程不在上面答话）
- 按窗口登记：连接表用 `Owned<K, V>`，`release_window` 里收（state.rs 那条测试会卡住漏收）
- 下载：照 D10 / D11，只从 Maven Central、钉版本、核 sha256、说清大小和许可证
- 入口包：数据库工具窗、结果表格、控制台的扩展全部懒加载；入口里只多导轨上一项（并进已有的 `{#each}`）
