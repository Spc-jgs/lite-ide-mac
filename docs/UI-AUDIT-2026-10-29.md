# 工作台 UI 与交互审查 · 2026-10-29

后续状态：用户认可后已实施本页修复方案，见 [实施与验证记录](UI-IMPLEMENTATION-2026-10-29.md)。以下保留审查时的现状与证据，不作为修复后的行为说明。

本轮只审查，不修改产品代码、图标、依赖或窗口配置。上一轮处理的是侧栏开合、构建入口和图标，不等于完成全应用审查。这次横向检查工作台、底部工具窗、状态栏、弹窗、表单、菜单、按钮、通知与键盘操作。

结论：现有视觉骨架可以保留，但**信息正确性、模态焦点、空间分配与操作可发现性存在实际缺陷**。没有理由再换一套图标、字体或圆角；先让现有界面在长内容、窄窗口、异步响应和键盘操作下可信、可控。

发现 **17 项：6 项 P1、11 项 P2**。P1 表示影响信息判断或主要操作；P2 表示有绕行办法的交互缺口或一致性问题。没有据此宣称全应用通过或不通过 WCAG，也没有给未经完整测量的性能、原生无障碍打分。

- [WAI：Menu / menubar](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/)：独立勾选和互斥选择的控件语义。
- [WCAG：Dragging movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)：提供不依赖拖动的单指针替代；这与键盘替代是不同要求，不能混称。
- [NN/g：10 usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)：状态可见、用户控制、一致性、错误恢复。

Apple 页面常规正文需要 JavaScript，本轮额外读取了官方 `.md` 版本的 split-views、menus、alerts，不以搜索摘要代替全文。

## P1：优先修复

### P1-01 · Git 文件读取失败被说成“没有文件变化”

位置：`src/lib/git/GitLog.svelte:151`、`:152`、`:352`。

`gitCommitFiles` 抛错后直接设置 `files=[]`，渲染与真正的空提交共用同一句空态。对该 IPC 注入读取失败后，界面确实显示“0 个文件 / 这次提交没有文件变化”。

影响：用户会根据失败的数据作出“提交没改文件”的判断。建议把载入、成功有数据、成功为空、失败分成明确状态；失败保留原因和“重试”，不显示成功为空的结论。

### P1-02 · 快速切换提交时，右侧可能展示上一条的文件

位置：`src/lib/git/GitLog.svelte:141`–`:158`。

effect 没有请求序号、销毁标记或当前 SHA 核对。先选 A 再选 B，注入 A=350ms、B=40ms 的响应后，标题选中的是 `f100000`，文件却是 `f2.java`。

影响：详情与操作对象失配。建议只接受当前仓库、当前 SHA 的最新结果；旧请求的成功、失败和 finally 都不能覆盖新状态。旧文件在新选择期间要明确清除或标记加载，不得看起来已经属于新提交。

### P1-03 · 底部面板拉高后，保存确认框和按钮被裁掉

位置：`src/lib/shell/Confirms.svelte:215`、`:476`；`src/App.svelte` 的 `.editor-island`；`src/app.css` 的 `.dialog`。

确认层相对编辑岛定位，顶部间距却按整个 viewport 的 `18vh` 算，编辑岛又裁剪溢出。1280×850 场景中拉高底部工具窗后，编辑岛高 153px、底边 y=197；保存按钮落在 y=281.75–309.75，完全在岛外。

影响：用户刚触发关闭文件，却看不到完整问题或按钮，只能猜 Esc 等绕行办法。同时，视觉只压暗编辑岛，输入却拦整个窗口，侧栏和底栏看起来仍可操作。

建议统一确认层的宿主与实际模态范围；按可用窗口高度限制对话框，正文可滚动，操作区保持可见；不能靠压缩底部工具窗后才能回答确认。

### P1-04 · 表单模态焦点会逃出，随后被守卫挡在外面

位置：`src/lib/settings/modal-host.ts:34`–`:41`；`SettingsDialog.svelte:162`；`RunConfigDialog.svelte:188`。

宿主只挡“焦点已在外面”的按键，没有 Tab 循环或 focusin 拉回。设置中从末尾“确定”按 Tab 后焦点离开 `.dialog`，继续 Tab 仍在外面。运行配置打开后也没有可靠地把初始焦点放入表单，末尾 Tab 同样逃出。

建议在现有宿主统一初始焦点、Tab / Shift+Tab 循环、失焦恢复和关闭归还焦点。不要把取消、回车、输入法处理分散成每个表单的一套。按钮型确认框已有 `cycleFocus`，应保留这些正确行为。

### P1-05 · Git 窄布局把最重要的提交标题挤到 0px

位置：`src/lib/git/GitLog.svelte:396`、`:505`–`:508`。

右侧固定 320px；左边作者 110px、时间 96px 不退让，标题是唯一主要收缩项。侧栏展开时实测：

| 窗口宽度 | 提交列表宽度 | 标题实际宽度 |
|---:|---:|---:|
| 1280 | 672 | 394 |
| 1000 | 392 | 114 |
| 900 | 292 | 14 |
| 800 | 192 | 0 |
| 720 | 112 | 0 |

建议按**工具窗实际可用宽度**退让，先收作者 / 时间等次要列，再折叠详情；保护标题的最小可读空间。小窗转为列表与详情之间的单栏导航，不靠整段 `overflow:hidden` 掩盖不可用。

### P1-06 · 长项目名和分支名把“停止”挤出标题栏

位置：`src/lib/shell/TitleBar.svelte:211` 起的 `.twidget`；`src/lib/run/RunWidget.svelte:136`。

在 720px 视口，把项目与分支文案换成合法的长名称做几何压力检查，停止按钮右边缘为 x=844.25，标题栏自身撑到 864.25px。固定挂件缺少整体优先级退让，单独省略每个名字仍不够。

建议优先保留停止 / 运行 / 当前运行配置，项目与分支依次压缩；常用动作的位置保持稳定。使用容器宽度和整体预算，不能每个挂件各自分配 240px 上限后就认为全局可用。

“更现代”在这个产品里应当具体表现为：状态说得清、错误能恢复、对象不串、空间可以调整、键盘不丢焦点、长内容仍能读。现有中性表面、有限圆角、克制颜色和密集列表符合工作台方向，无须增加渐变、动效、卡片或再换图标。

## 建议的设计顺序与验收口径

1. **先修可靠性**：Git 响应 / 错误状态、表单焦点、确认层可见性。验收要包含故意失败、乱序与底部工具窗占大半窗口的场景。
2. **重整底部工具窗的尺寸规则**：整体高度、内部宽度、说明与结果区、最大化 / 恢复、布局复位。保存已选尺寸和恢复方式，保护编辑器与主要数据列。
3. **收齐状态一致性**：保存中取消、错误字段定位、动态键位、菜单能力、通知焦点。用一套控件状态表达默认 / 悬停 / 聚焦 / 禁用 / 忙碌 / 成功 / 失败。
4. **最后做排版微调**：长标题、元信息、空态与窄窗列收纳。保留图标、字体和既有视觉令牌，不扩大成全应用换皮。

底部工具窗建议保留“Git → 提交历史 / 控制台”的层级。头部右侧给最大化 / 恢复、隐藏；局部操作仍放局部工具栏。列表与详情之间可调宽；详情内部给可控的摘要与文件区。可用区域过窄时进入单栏列表 / 详情导航，阈值应按内容区域测量，不只按窗口宽度。

后续真实 `.app` 验收只走测试身份与测试通道，并单独记录：鼠标命中、Tab 完整循环、VoiceOver、系统缩放、不同壁纸 / 材质、菜单与当前窗口、两个项目窗口隔离。浏览器可复现的问题可以先修；原生差异仍要保留为未验，不能因为单测通过而升级结论。
