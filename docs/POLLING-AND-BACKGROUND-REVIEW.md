## 1. 怎样选择机制

这里的“最好”指本项目约束下兼顾正确性、反馈延迟、空闲成本、故障恢复和维护成本，不是采用最多机制。

| 变化来源 | 推荐机制 | 必须保留的边界 |
|---|---|---|
| 应用自己掌握的变化：标签关闭、文档事务、Git 命令完成 | 在状态的主人处发通知；消费者按需订阅，批量合并 | 先订阅再取初始快照，或用版本补齐订阅窗口；关掉消费者就取消订阅 |
| 外部状态：文件追加、外部改文件、路径删除再出现 | 原生文件通知作为失效提示，再读实际状态；焦点/重新连接时校准，必要时小范围低频轮询 | 原子替换、事件合并/溢出、监听失败、网络卷、不存在路径；不能将每个事件当成一次精确修改 |
| 连续数值：JVM 堆、GC 曲线 | 低频、有限历史的采样 | 有人看或有实际用途时才采样；同一对象最多一个请求在途；隐藏/停止后不再采 |
| 有限等待：启动后的端口发现、停止后的进程退出 | 有事件就等事件；缺少可靠事件时用有截止/明确终止条件的探测 | 单次查询也要能结束；总等待受限；目标结束就取消。进程组仍存活时的监护可随组存续 |
| 草稿恢复、输入停止后的保存 | 内容变化触发，防抖合并，并设连续编辑下的最长备份间隔；恢复/失焦/退出补写 | 备份与保存用户文件语义分开；可靠性和冲突保护优先于省写入 |

异步状态写回另有独立要求：**停止未来 tick，不会取消已经发出的请求。**请求返回后还要核对窗口/项目/句柄/文档版本是否仍有效。防抖、限制并发、丢弃过期结果解决的是三个不同问题。

这些是本次基于源码及外部资料作出的设计建议，尚未全部实现；不要将本表当成已存在的统一调度层。

## 2. 现有轮询清单与逐项判断

### 2.1 标签、编辑器及持久化

| 对象与代码 | 当前行为及理由 | 判断与适合本项目的做法 |
|---|---|---|
| Java / 通用 LSP：`src/lib/editor/java-lsp.ts::wire`、`lsp-generic.ts::wire` | 首次使用后每 1 秒核对 `opened` 与标签列表，消失才发 didClose。切换标签也销毁 EditorView，因此不能在视图销毁时关闭文档。无文档时立即返回，但两个定时器仍存在；各 WebView 初始化后各有自己的定时器 | 文档生命周期的判断是对的。长期更适合由标签/文档状态的主人通知关闭，集中清诊断及 opened；最小改法是 opened 非空才运行，清空就停。低优先级，未测出明显能耗问题；不能把 `.ts` 不能写 `$effect` 当成只能轮询的理由 |
| Structure：`src/lib/search/StructureView.svelte` | 挂载且有编辑标签时每 400ms 查当前视图、光标行和不可变 `Text` 身份；正文不变不提取符号，卸载清 timer | 当前范围和清理合理。推荐面板打开时订阅活动编辑器的更新：光标只改高亮，文档变化防抖后提取符号；面板关闭取消订阅。可以复用已有 updateListener 加一个按需订阅出口，不必给所有编辑器安装重计算逻辑 |
| 外部修改：`src/App.svelte` → `docs.checkExternalChanges` | 每 10 秒查已打开编辑文件的 mtime/size；焦点与 `fs-changed` 也会触发。不会定时遍历整个项目 | 当前已经是“事件 + 兜底”，保留有理由。完善 watcher 健康/覆盖边界后，再决定仅对未覆盖文件或降级状态轮询；不要直接删除兜底。**先修 §4 R1 的重载竞态**，改触发机制本身修不了数据覆盖 |
| 恢复草稿/自动保存：`src/App.svelte` → `persist.tickDrafts` / `docs.autosaveSweep` | 每 4 秒兜底；输入还有 500ms 防抖，失焦/退出会补写。恢复出来已经脏、但没再输入的草稿靠 sweep 覆盖。无脏标签不写，相同快照也不重复写 | 可靠性需求成立，保留现状。长期可在首次变脏时启动备份期限，内容变化防抖，并设 max-wait 防止连续输入永远推迟；恢复脏文档时主动登记。需要以崩溃前可丢几秒内容明确恢复目标，再比较真实写入与主线程耗时，不能只追求零 timer |

**更正结构面板的描述：**它当前调用 `fileSymbols(path, doc.toString())` → `outlineOfText` → 新建 `EditorState` → `ensureSyntaxTree`，复用的是 Lezer/符号提取方案，**没有直接复用活编辑器那棵语法树**。`outlineOfText` 的解析预算为 300ms、输入上限为 2,000,000 字符；这不是“只做两个比较”的全部成本。`fileSymbols` 最多缓存 16 个文本/符号结果，按条数有界，但不是按字节计费，也不是命中时更新顺序的严格 LRU。是否需要改变容量取决于实测，不能把理论字符总量当成当前占用。

复用活编辑器语法树时还需处理“doc 没变，但懒加载语言/后台解析推进后 tree 变了”；不能只订阅 docChanged，否则可能把第一次空结果一直保留。当前 `outline.ts` 的缓存注释已经记录过这类失败形状。

### 2.3 后端维护与短时等待

| 对象与代码 | 当前行为及理由 | 判断 |
|---|---|---|
| 空闲语言服务器：`java.rs::spawn_janitor`、`langs.rs::spawn_reaper` | 首次启用后各一条进程级线程每分钟检查；无文档且空闲 10 分钟回收服务器。空表时仍有检查 | 低频清理换简单可靠，保留。只有大量服务或精确回收期限需要时才考虑最近截止时间 + 条件变量，不为消灭一分钟一次的检查引入复杂计时框架 |
| 任务进程组：`tasksvc::Task::start` 的 wait 线程 | 组长 `child.wait()` 是阻塞等待。组长退出但后台成员仍活着时，每 200ms 查进程组，直到消失 | 进程组仍占资源时不能假装任务已结束。保留；不要把子进程退出通知等同于整个组退出通知。是否降频取决于停止状态反馈与实际长时间后台任务数量 |
| procutil 收尸：`procutil::spawn_reaper` | 没待收进程时阻塞 recv；有未收进程时约 200ms try_wait | 已按是否有工作控制唤醒，保留。不能仅因使用 recv_timeout 判空转 |
| 更新检查：`update.rs::start` | 启动延迟 30 秒，之后每 12 小时按设置检查；关检查不发请求，但线程仍等下一轮 | 产品自动更新的低频策略，保留。允许延迟、失败后不密集重试，未来再按需求评估恢复网络/睡眠唤醒后的检查；与资源验收按需运行是两回事 |
| 凭据监听、调试启动、停止宽限等 | 在具体操作期间等连接/端口/退出，有相应终止/超时路径 | 按操作审查，不与常驻 UI timer 混算。问题是能否取消、能否结束、是否在主线程及单次工作是否有界，不是有没有 sleep |

AI 启动时每秒更新耗时数字属于显示计时，结束即停；`main.ts` 每 3 秒数编辑器/DOM 的诊断仅在 debug 开启时运行。输入防抖、复制提示复位、启动懒加载延迟属于一次性 timer。这些不能都计作业务状态轮询。本表覆盖已搜索到的主要生产路径，非所有 await/sleep/重试的穷举证明。

## 3. 别人怎样做，哪些值得学

资料查阅日为 2026-10-29；网页及 `main` 分支会变。以下只概括实际查到的机制，不声称所有 IDE 都一样，也不将竞品的频率当成本项目标准。

1. **VS Code 文件监听采用原生事件，也有定向轮询退路。**公开说明包含监听请求去重、重叠根合并、文件复用已有递归监听；路径消失时复用父级监听或每 5 秒检查恢复。值得学的是复用、失效恢复和兜底范围，不是复制完整文件服务。[官方 File Watcher Internals](https://github.com/microsoft/vscode/wiki/File-Watcher-Internals)
2. **IntelliJ VFS 将通知与刷新分开。**原生 watcher 提示哪些文件变化，异步 refresh 对实际状态；没有 watcher 时走刷新范围遍历，切回应用也是校准机会。对本项目的启发是“事件提示失效，读状态确认”，不用建立 IDEA 那样的持久化 VFS。[官方 VFS 文档](https://plugins.jetbrains.com/docs/intellij/virtual-file-system.html)
3. **IDEA 自动保存同时有事件与空闲时间触发。**运行/构建/关闭等事件、切应用、可配置的空闲保存并存，说明为可靠性保留时间触发很正常。草稿恢复备份与写用户源文件仍是不同承诺。[官方保存文档](https://www.jetbrains.com/help/idea/saving-and-reverting-changes.html)
4. **VS Code 文本重载保留文档版本并在读完后复核。**`resolveFromFile` 在 await 前记 versionId，返回后版本不同就不覆盖；保存路径另有串行化及版本判断。本项目不需要照搬类体系，但需要同样的数据保护约束。[官方文本模型源码](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/services/textfile/common/textFileEditorModel.ts)
5. **VS Code 的大纲结果按模型版本/提供者缓存，缓存有界，模型移除时删项，并支持取消。**值得学的是结果版本、取消和归属，不是改用它的语言服务器路径。[官方大纲源码](https://github.com/microsoft/vscode/blob/main/src/vs/editor/contrib/documentSymbols/browser/outlineModel.ts)
6. **CodeMirror 已提供文档/选区更新与销毁钩子。**可以按面板生命周期消费现有编辑器更新，没必要在轮询和“每次按键全量算大纲”之间二选一。[官方 View 参考](https://codemirror.net/docs/ref/#view.EditorView.updateListener)
7. **文件通知不是绝对可靠的数据真相。**notify 官方列出网络卷无通知、编辑器保存方式差异、父目录删除及大量事件等限制。这支持保留受限校准，而非立即删掉 10 秒兜底。[notify 已知限制](https://docs.rs/notify/latest/notify/#known-problems)
8. **Apple 建议减少无用 timer，能收事件就收事件，必须用 timer 时及时停并允许时间弹性。**这是 macOS 能耗设计原则，不提供“超过几个 timer 就有害”的统一红线；JS timer 也不能直接套用 NSTimer tolerance API。[Apple macOS 能耗指南（归档）](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/Timers.html)

## 4. 除轮询之外，本轮确认或发现的缺口

P1 表示数据保护或明显资源放大应优先修；P2 表示有具体触发条件的正确性/负载边界；观察项不直接升级为缺陷。下列描述是评审时状态，修复进展见 §7。

### R1 · P1：外部重载会覆盖等待期间的新草稿（真实状态层已复现）

- 位置：`src/lib/state/docs.svelte.ts::checkExternalChanges`，`Editor.svelte` 的同文件外部重载分支。
- 形状：标签初始干净 → 外部文件变化 → 检查通过 dirty 判断并开始 readText → 用户输入并切走，`stashDraft` 已保存新草稿 → 旧请求返回后 `Object.assign(tab, settled(...))` 清掉草稿和 dirty。
- 本轮通过仓库 runes loader 运行**当前 Docs/Tabs/IPC 包装代码**，仅把 IPC 读返回时间用 gate 控制；没有复制待验证函数，也没操作真文件。输出：等待期间 `draft="OLD + LOCAL INPUT", dirty=true`；返回后 `content="EXTERNAL", draft=null, dirty=false, conflict=false`。
- 这证明状态层能清掉新草稿；不将其冒充整套真应用/按键验收。活编辑器有撤销栈不等于所有切走的草稿能找回。
- 建议：每个文档记录修订代次；读之前捕获标签身份/路径/模式/代次，回来重新取当前标签并核对。期间发生编辑/保存/改名/关闭/新一轮重载时，丢弃过期回包或标冲突。单查 dirty 不够覆盖“编辑又撤销”“保存改变基线”等次序。
- 完成标准：正常干净重载仍生效；慢读期间输入、切走、保存、改名、关闭后重开，以及两次重载逆序返回，都不吞字、不清错误基线。复现上述失败后再修，修后确认保护生效。

### R2 · P1：JSON 格式化输出没有容量上限（当前 Rust 函数已复现）

- 位置：`crates/httpsvc/src/json.rs::reindent`，`send_capped` 的 pretty 分支。
- 现有保护：原始响应最多 32 MiB，仅输入不超过 8 MiB 才尝试格式化；这两条不能限制缩进扩张后的输出。
- 本轮用临时 rustc 探针直接引用当前 `json.rs`：1000 层合法数组，**2001 B → 2,004,001 B，约 1001.50 倍**。只做小样本，没有制造 OOM，也不能据此断言日常响应已经导致高内存。
- 建议：向输出追加前做字节预算检查；超限返回“未格式化”并保留原始响应/原次序与数字，不先生成完整大结果再判超限。输入、转换结果、保留文件各自需要预算。
- 完成标准：正常响应仍格式化且保持原值；嵌套/长字符串等输入在预算内结束，超限回退原文并说明未格式化，保留文件大小有界。

### R3 · P2：丢弃过期 Git 结果，不会限制重复查询（真实状态层已复现）

- 位置：`src/lib/state/git.svelte.ts::refresh`；触发可来自保存、焦点、手动动作和合并后的文件事件。
- 已有正确保护：`refreshSeq` 与仓库身份阻止过期结果覆盖最新状态；这是应该保留的。
- 缺口：每次调用仍立即并发启动 git_status 和 git_stash_list。用当前 Git 状态类、受控慢 IPC 连续调用 10 次 refresh，首批完成前发出 **20 次查询、20 次同时在途**。这是 IPC 调用计数，不是真机同时 20 个 git 的性能实测。
- 事件每 300ms 合并一次只限制通知速率；若查询更慢，仍可能叠加。事件驱动同样需要背压，不能靠换成事件自动解决。
- 建议：每个仓库最多一轮刷新在途，期间的变化置 rerun 标志；完成后至多补一轮，保留需要刷新历史的意图。错误/换仓库也要清理；用户写操作与状态读不能套同一个排队规则。
- 完成标准：慢 IPC 下突发刷新最多一轮在途、最终数据含最后一次变化、history 意图不丢、切仓库不串；再测大仓库的进程峰值和刷新尾延迟。

### R4 · P2：部分异步采样缺少单次在途、过期回包或错误收尾（源码确认，影响待专项）

- `ServicesView` 的堆 interval 没有 in-flight guard，也未在 await 后判断 effect 是否已销毁/服务集合是否换代。端口循环也只清尚未触发的 timeout。旧回包仍可写入组件状态。
- `LogPane` 索引/过滤进度有 stop/dead 防止已销毁结果写入，但没有单次在途限制；interval 内的 await 抛错不会被创建 interval 外层的 try/catch 捕获。句柄失效/IPC 失败时存在重复失败和 Promise rejection 路径。tail 有 refreshing，但没有 await 后的失效判断。
- 这些是可由代码确认的缺少边界，不代表普通机器上已经发生大量排队或定时器泄漏。`clearInterval` 清理本身已经存在，不能写成“完全没清理”。
- 建议：局部采用“本轮结束再安排下一轮”或 in-flight guard，加 generation/dead 核验与明确错误/完成收尾。临时轮转失败可继续；永久失效要停或显式降级。无需引入覆盖全项目的通用调度框架。
- 完成标准：注入慢于周期的请求、逆序回包、失败，以及 await 中途关闭/换目标；每对象至多一轮在途，旧结果不覆盖，失败不无限重复，不留下未结束的进度项。

### R5 · P2：文件监听缺少运行期失效/重扫信号处理（源码确认，原生故障未复现）

- 位置：`crates/fsservice/src/watch.rs` 的 watch/watch_file/watch_paths 回调。`Err` 直接返回；未单独处理 `need_rescan`，根 watcher 的空路径事件不会置变化标志。watch_paths 的**应用内路径 cap** 已有 overflow，不能误说完全没处理溢出。
- 现有保护：初始化失败返回 Err；焦点刷新和 10 秒打开文件校准仍在。局限是 10 秒只校准已打开正文，不自动修复所有文件树/搜索索引/语言索引状态。
- 风险触发：运行期 watcher 错误、后端提示事件不完整但没有可处理路径时，消费者没有收到“请校准/已降级”。本轮没有模拟系统丢事件，也没有证据证明目前真实项目已经不同步。
- 建议：在现有通知中区分失效/需重扫，合并后按已知范围校准；持续监听失败提供一次明确提示与受限降级，避免每个文件另起 watcher 或无条件整树高频扫描。
- 完成标准：注入 Err、无路径 rescan、cap overflow、删除后重建、原子替换，确认校准能恢复且有上限。原生行为在隔离 fixture 补测。

### R6 · 观察项：结构重复解析、同步快照和保留容量

- 结构重复解析已确认（§2.1），但“300ms 解析预算”不是实测每次花 300ms。先测代表性大源码编辑时的主线程 p95/p99、解析次数、转换字符数，再决定复用树/按需订阅的排期。
- `persist.write` 会在前端同步序列化/写 localStorage；已有 400ms 防抖、相同内容去重，草稿每份 500,000 字符、总计 2,000,000 字符上限。容量有界不等于尾延迟一定好；也没有证据说明它现在卡顿。先测接近限额的恢复/持续编辑，确有瓶颈才分离小布局与正文备份，不预建数据库或日志框架。
- 本地历史有每文件容量/版数/年龄限制，修剪只发生在再次记录该文件时；HTTP 按项目保留约 50 份响应，缺全局字节预算。静置目录不会仅因过期自动消失，这是策略缺口，未证明当前磁盘异常。先给用户可理解的容量承诺，再决定访问/写入/启动分批回收，不用常驻清理器。
- 两种 LSP 的 viewsOf 可能保留空 Set 键，诊断有关闭路径之外的缓存写入。空键不是 EditorView 对象泄漏的证明；修改相关路径时清理，若要宣称诊断缓存泄漏需测完整事件生命周期。
