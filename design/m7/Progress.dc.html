进度与取消
这是选择子进程要自己付的那一半代价。付得起 —— 但**必须先看清 git 的进度到底长什么样**， 不然按常规的「按行读 stderr」写出来的东西，一个字都读不到。
实测：本地 clone 一个 1248 对象的仓库
stderr 的原始字节
0000160    \r  r  e  m  o  t  e  :     C  o
0000240        \r  r  e  m  o  t  e  :     C
0000320            \r  r  e  m  o  t  e  :
进度是用 回车 \r 分隔的， 不是换行 —— 因为它本来是给终端「原地刷新」用的。
7
按 \n 分得到的行数
411
按 \r 分得到的段数
17,545
stderr 总字节
按行读只能读到 7 段，而且全在结尾 —— 进度条会一直是 0%，然后突然 100%。
切开之后的内容
remote: Enumerating objects: 1248, done.
remote: Counting objects:   7% (88/1248)
remote: Counting objects:   8% (100/1248)
        …
remote: Compressing objects: 100% (498/498)
Receiving objects:  62% (774/1248)
Resolving deltas: 100% (722/722), done.
四个阶段，格式统一：阶段: 百分比% (当前/总数)， 结束那段带 , done.。
单段最长 86 字节 —— 上限很小， 但总量无上限（对象越多段越多）。
于是这么读
1
按 \r 和 \n 一起切。 流式读 stderr，遇到任一个就切一段。段长有 86 字节这个天然上限， 但缓冲区仍要设闸 —— 万一撞上一个不带分隔符的怪输出，无上限的 read_to_end 就是下一个 git diff 吃掉 30MB 那件事。 判据和 AGENTS.md 那条一样：新加任何「跑子进程读 stdout」 的功能，先问一句这东西的输出有上限吗。
2
往前端推之前先节流。 411 段是一个本地 clone、 1248 个对象的量；真去网上拉一个大仓库是几千段。 Channel 一段推一次的话，IPC 和 Svelte 的响应式 会被一条进度条打满 —— 而人眼一秒看不了 60 次百分比。
节流判据：阶段变了、或者百分比变了且距上次推送超过 100ms。 阶段变了必须立刻推（那是四次里的一次，不能被节流吃掉）。
3
解析失败不是错误。 git 的进度文案不是稳定接口（LC_ALL=C 只保证是英文， 不保证措辞不变）。解析不出百分比就原样把那段文字推上去， 界面显示成一行状态而不是进度条。
绝不能因为解析不出来就当操作失败 —— 那会把一次成功的 fetch 报成红的。
取消：kill 子进程，句柄表复用 pty 那套
AppState 里已经有一张 pty 的句柄表和 kill_pty，远程操作用同一个形状。

但要抄对 pty 那次踩过的坑： kill_pty 原来持着整张表的锁就地析构， 一挂就是所有终端操作全堵死。远程操作这边同样 先从表里摘出来，再在锁外 kill。

收尸也要有界：wait() 换成有上限的 try_wait() 轮询 —— 宁可留一个僵尸到进程退出， 也不能让界面永久卡死（同 ptysvc）。
取消一次 fetch 是安全的，push 要说清
fetch / pull 的第一步：git 把对象写进临时 pack， 最后才原子地更新 ref。中途 kill 掉的后果是留下一个临时文件， 下次 git gc 清掉 —— 本地仓库不会坏。

push 不一样：kill 的是本地这一端， 而远程可能已经收完了。所以 push 进行中不给「取消」，只给「在后台继续」 —— 一个点了之后状态不确定的取消按钮，比没有按钮更糟。
（真要停，用户可以退出应用；那时的语义同样不确定，但至少他知道自己在做什么。）
这段代码能单测
切段和解析是纯函数，跟子进程无关： 喂一串字节，吐一串 Progress。所以它落在 crates/gitsvc 里、不依赖 Tauri， 而且要用上面那 17,545 字节的真实 stderr 当测试数据 —— 不是自己编一段格式漂亮的。

至少这几条要验红：\r 分隔认不出来（退化成 7 段）、 节流把阶段切换吃掉了、解析不出百分比时报成了失败、 分段边界正好落在一段中间（流式读一定会遇到）。
