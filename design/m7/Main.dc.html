M7 拉取与推送 · 方案
先调研再设计。这张是底层选型： 三条路量下来，留在子进程。
「各家是怎么做的」那张是这张的修正 —— 按主流对齐之后，这里的凭据和 push 界面两节有改动，以那张为准。
一 · 三条路，都量过
子进程 git（现状） git2 / libgit2 gix（纯 Rust）
push ✓ ✓ ✗ 没有 —— 官方状态页把 push 列在 1.0 路线图上，「create (thin) pack」还没做。 M7 的终点就是 push，这一条直接出局。
凭据 ✓ 白得 —— git 自己跑 credential helper 和 ssh-agent， 和用户终端里的行为一模一样。 实测：精简环境 + GIT_TERMINAL_PROMPT=0 的 fetch 退出码 0 ✗ 只给接口，不给方案 —— libgit2 把凭据甩给调用方回调， 你要自己写「ssh-agent → helper → 用户名密码」的优先级， 还要自己防 libgit2 无限重试。 cargo 为这件事专门写了一个 with_authentication ⚠ gix-credentials 在「usable, initial development」档
进度 ⚠ 要解析 \r 分隔的文本 ✓ 结构化回调，直接给数字 —
取消 ⚠ kill 子进程 ✓ 回调返回 false —
体积 0 +0.85 MB —— 实测（空壳 0.29 → 带 git2 1.13， release + LTO + strip）。二进制现在 5.12 MB， 这是 +17% —
依赖 0 13 个传递依赖，含 libgit2-sys —— 一个要用 cc 现编的 C 库 204 个 crate
结论：留在子进程
gix 没有 push，出局。 剩下的是子进程和 libgit2 之争， 而 libgit2 在最难的那件事上不提供解决方案 —— 凭据。它给的是接口，方案还得自己写，而且要写得比 cargo 那个 with_authentication 更小心（那是个带无限重试防护的函数）。

它换来的是两样：结构化进度、结构化取消。代价是 0.85MB + 一个要现编的 C 依赖。而那两样的自制版本，各自只有几十行 —— 见后面两张画板。

这和「用 trash crate 而不是自己往 ~/.Trash 里 rename」不矛盾。 那次的判据是「系统 API 有一堆自己的规矩，该由维护着的库去对」； 这次的判据是同一条 —— git 的凭据规矩该由 git 自己去对， 而 git 这个可执行文件就是那个「维护着的实现」。 libgit2 反而是把这套规矩重新实现了一遍的那一方。
二 · 命令面
命令git 实参说明
git_fetch(root, on_progress) fetch --progress --prune origin 只读。--prune 让远程删掉的分支在本地也消失 —— 不加的话分支面板里会一直挂着已经不存在的 origin/*
git_pull(root, mode, on_progress) merge --ff-only / --no-ff / rebase 先 fetch 再本地合并，不用 git pull —— 见下面「pull 拆成两步」
git_push(root, set_upstream, on_progress) push [--set-upstream origin <br>] force 做不做待定 —— 主流（IDEA）做，藏在 Push 下拉里且是 --force-with-lease； issue #8 里你写的是不做入口。见「各家是怎么做的」那张右下角
git_cancel(id) — kill 那个子进程。句柄表和 pty 用同一套（AppState）
pull 拆成两步，不用 git pull
git pull 是 fetch + merge 的复合命令，而它默认建合并提交。 问题不在于合并本身，在于出错时分不清是哪一半错了： 网络断了和合并冲突了，退出码都是非零。

拆成两步之后：
第一步 fetch —— 走网络、要凭据、要进度、可取消， 但绝不动工作区。失败了就是纯网络/凭据问题。
第二步本地合并 —— 不走网络、瞬间完成、 失败就是冲突，而冲突有 MergeView 接着。

默认 --ff-only：能快进就快进， 不能快进时停下来问（合并还是变基）。 这样永远不会「拉一下，凭空多出一个合并提交」。
push 是第一个会改到别人东西的动作
在此之前所有操作只碰本地盘。三条：

一、没有 force。 连 --force-with-lease 都不做入口 —— 真要强推的人会去开终端，而那个动作值得多花那十秒。
二、--set-upstream 只在没有上游时出现， 而且要把「它要建立什么」写在按钮旁边，不是一个沉默的开关。
三、被拒绝要说人话。 non-fast-forward 的真实含义是「远程比你多了东西」， 下一步是先拉。git 的原文（Updates were rejected because…） 要转译，但原文也要留着能展开看 —— 转译错了的时候人得有办法绕过我们。
三 · 代码放在哪
1
crates/gitsvc —— 业务全在这儿，不依赖 Tauri。 新增 remote.rs：fetch() / merge() / push()， 进度通过一个 FnMut(Progress) 回调往外抛， 取消通过一个 Arc<AtomicBool> 往里传。 这两个都不是 Tauri 的类型 —— 所以这一层能脱离 GUI 单测，和现有五个 crate 一致。
2
src/commands.rs —— 只解包、查句柄、转错误。 把 tauri::ipc::Channel 包成上面那个回调， 把句柄表里的 flag 传下去。一行业务都不写， 这条是 AGENTS.md 里既有的规矩。
3
进度通道复用 pty 那套。 tauri::ipc::Channel<T> 已经在 pty_spawn 上用着了，是这个仓库里 「Rust 往前端持续推数据」的既有做法 —— 不新起一套。
做的顺序：fetch → pull → push → askpass → 后台 fetch
askpass 排在 push 之后**不是因为它不重要** —— 是因为前三步用现有凭据（钥匙串里已经有了，实测通的）就能全部跑通并验收， 而 askpass 服务的是「第一次连一个新远程」。 把它排前面的话，前三步的验收要等一整套 socket + 弹框先写完。
后台 fetch 排最后：它默认关，而且只有前面都稳了才敢让它自己跑。
顺序本身就是判据。 fetch 只读、失败没有后果 —— 拿它把「凭据」和「进度/取消」这两块地基趟平。 pull 会产生冲突，而冲突有现成的 MergeView。push 最后。
反过来先做 push 的话，第一次撞上的就是 「凭据没配好 + 已经改了远程 + 不知道改成什么样了」。
